# 2026-06-30. Локальный fallback и следующие задачи

## Контекст дня

VPS снова стал недоступен из-за проблем в дата-центре. Сервер не отвечал по сети: SSH, ping и проверка TCP/22 не проходили. Чтобы бот продолжил работать, был поднят локальный экземпляр с production-настройками и локальной копией скачанного backup SQLite.

Важно: локальный запуск использует тот же Telegram bot token, поэтому одновременно с ним нельзя запускать production-контейнер на VPS. Когда VPS восстановится, локальный контейнер нужно остановить до запуска бота на сервере, иначе Telegram вернёт конфликт polling.

## Техническое пояснение по памяти

Обсуждалось, почему после Google Sheets операций память процесса может расти ступеньками.

Вывод: проблема не обязательно в прямой утечке Google-библиотеки. Чаще связка Python, обработка крупных JSON-ответов и системный allocator удерживает уже выделенную память и не сразу возвращает её операционной системе.

Поэтому текущие меры остаются оправданными:

- `MALLOC_ARENA_MAX=2`;
- `gc.collect()` после polling-циклов;
- `malloc_trim(0)` на Linux;
- отдельный Google API executor;
- уменьшение чтения больших диапазонов.

## Анализ оптимизации обращений к Google API

Текущая версия уже содержит базовые защитные меры:

- все Google API операции выполняются через отдельный `ThreadPoolExecutor(max_workers=1)`;
- включен retry/backoff для `429`, `5xx` и временных сетевых ошибок;
- Google discovery cache отключен через `cache_discovery=False`;
- dashboard синхронизируется через SQLite outbox и одним batchUpdate;
- новый `bulk_reservations` workflow регистрирует несколько строк одним batchUpdate;
- завершенные legacy bulk-пачки проверяются редким архивным scan, а не каждым polling-циклом.

Главное текущее узкое место — polling одиночных заявок. Сейчас он группирует заявки по листу и читает диапазон вида:

```text
A1:X{max_seen_row}
```

Это лучше, чем полный `A:X`, но при росте числа строк на листах всё равно расходует лишние read quota. Для пилота на невысокой нагрузке это приемлемо, но для 80 пользователей станет одним из главных источников риска по Google quota и задержкам.

Что стоит оптимизировать дальше:

1. Перевести polling одиночных заявок на точечный `values.batchGet` по известным строкам.
2. В одиночной отправке заменить полный поиск `application_id` по листу на Google `developerMetadata`.
3. При подготовке листа сначала читать только диапазон шапок/маркеров, например `A1:X20`, а полный read делать только когда реально нужно найти точку вставки.
4. После стабилизации новой массовой модели ограничить или отключить legacy bulk scan.

Вывод: для текущего пилота схема рабочая. Для масштабирования нужно сначала уменьшать широкие чтения рабочих листов.

## Операционные риски

1. Пока бот работает локально, VPS-бот должен быть остановлен.
2. Локальная БД основана на backup от 2026-06-28, поэтому если на VPS после этого были изменения и они не попали в backup, локальная БД может быть не полностью актуальной.
3. Google Sheets остаются production, поэтому действия локального бота пишут в реальные таблицы.
4. При восстановлении VPS нужно решить, какую БД считать источником правды: серверную или локальную аварийную.

## Итог дня и замечания для эксплуатации/разработки

### Что важно помнить в эксплуатации

- Одновременно может работать только один контейнер с одним Telegram bot token. Если поднят локальный fallback или тестовый бот с тем же token, второй экземпляр получит Telegram polling conflict.
- Локальный тестовый контейнер, запущенный без `-p`, использует project name `alfa-auto-requests` и volume `alfa-auto-requests_bot-data`. Для полностью изолированных тестов лучше запускать с `-p alfa-auto-test`, тогда будет использоваться volume `alfa-auto-test_bot-data`.
- Локальный production fallback не пересекается с текущим тестовым volume: он использует bind mount `tmp/local-prod-data`, а тестовый контейнер использует Docker named volume.
- В `docker-compose.yml` задан `SQLITE_PATH=/data/app.db`, поэтому значение из `.env.local` может не примениться, если оно не переопределено в compose override. Это нужно учитывать при проверке, какую БД реально использует контейнер.
- В `.env.local` нет `GIGACHAT_*` credentials. Значит тестовый контейнер не подходит для полной проверки реального GigaChat без дополнительной локальной настройки.
- После изменений по срочным CHIPS нужно вручную проверить тестовую Google Sheets: одиночная срочная CHIPS-строка и массовый срочный CHIPS-резерв больше не должны получать бежевую заливку.

### Что важно учитывать в разработке

- Создание bulk reservation теперь зависит от Google `developerMetadata`. Если metadata lookup временно недоступен, безопаснее не вставлять строки, чем рискнуть дублем.
- Section-lock для bulk creation должен удерживаться до завершения SQLite `complete_bulk_reservation_creation_and_shift()`. Нельзя снова выносить SQLite row-shift за пределы lock, иначе вернётся гонка с одиночной вставкой.
- Регистрация bulk reservation должна восстанавливать dropdown и для `Редактор`, и для `Статус`. `updateCells` не должен затирать `dataValidation`.
- При создании массового резерва нужно очищать inherited background, потому что Google Sheets может наследовать формат предыдущих строк при `insertDimension`.
- Для листа `Срочные` текущая логика переустанавливает conditional formatting rules, чтобы убрать старое правило срочности, которое красило CHIPS. Если в будущем на лист вручную добавят дополнительные conditional formatting rules, бот может их удалить при подготовке листа.
- Новая массовая модель регистрирует строки как обычные одиночные заявки, без `batch_id`. Dashboard и polling должны рассматривать их именно как одиночные заявки.
- Пустые строки, оставшиеся после регистрации резерва, не считаются будущей очередью бота. Это нужно явно объяснить пользователям.
- До масштабирования на 80 человек остаются важные оптимизации Google API: точечный polling одиночных заявок, metadata для поиска одиночных строк и ограничение широких reads структуры листов.

## Дополнение: незакоммиченные изменения после тестирования срочных CHIPS

После ручной проверки тестового контейнера обнаружено, что срочные CHIPS-заявки визуально заливаются бежевым фоном, хотя для CHIPS это не нужно. Проблема проявлялась в двух сценариях:

- одиночные срочные CHIPS попадали под общее conditional formatting правило срочности;
- массовые срочные CHIPS могли наследовать фон предыдущих строк при `insertDimension`.

Что исправлено:

- правило срочной заливки теперь исключает CHIPS: строка подсвечивается как срочная только если `Срочная = Да` и `Тип изменения != CHIPS`;
- при подготовке существующего листа `Срочные` бот удаляет старые conditional formatting rules и заново ставит штатные правила статусов и срочности уже с исключением CHIPS;
- при создании массового резерва бот сначала очищает inherited background по всему вставленному диапазону, а затем заново подсвечивает только обязательные пользовательские колонки;
- подсветка массовых обязательных полей сохранена: `Закрепленный сценарист` остаётся нейтрально-голубым, остальные обязательные поля остаются светло-жёлтыми;
- добавлены regression-тесты на новое правило срочности и очистку inherited background.
