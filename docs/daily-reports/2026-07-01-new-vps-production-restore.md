Старый VPS больше не рассматривается как рабочая площадка. Арендован и подготовлен новый сервер в Казахстане:

- VPS host: `206.223.244.31`;
- пользователь: `root`;

- production Compose: `docker-compose.prod.yml`;
- текущая production-версия: `pilot-20260630-2310-06dd685`.

Также прошел созвон с руководителем по возможной миграции из Telegram в A-Chat/eXpress. На созвоне выяснилось, что получение доступа к тестовой и production-системе связано с бухгалтерскими и согласовательными процедурами, потребуется много доступов, а также нужен IT-лид или ответственный со стороны внутренней инфраструктуры, который сможет взять ответственность за этот проект.

## Что сделано

- Подготовлен VPS: Docker Engine, Compose plugin, log rotation Docker, swap, fail2ban, unattended upgrades, рабочие каталоги.
- Собран и загружен production image `alfa-auto-requests-bot:pilot-20260630-2310-06dd685`.
- На сервер переданы production `.env`, `credentials.json`, `docker-compose.prod.yml` и локальная production-БД, которая использовалась сегодня.
- SQLite перенесена в Compose volume `alfa-auto-requests_bot-data`; volume пересоздан через Compose, чтобы не было предупреждений о manually-created volume.
- Контейнер запущен и проверен:
  - `docker compose ps` показывает `healthy`;
  - `python -m app.health` возвращает `ok`;
  - SQLite `PRAGMA integrity_check` возвращает `ok`;
  - свежие логи без `ERROR`, `Traceback`, `TelegramConflictError`, `HttpError`, `429`, `500`.
- Локальный мониторинговый dashboard переключен на новый VPS и успешно собрал snapshot:
  - `source_host = 206.223.244.31`;
  - `container_health = healthy`;

- Из production-БД удалена потерянная заявка `7C4C4BA4`; перед удалением создан backup `/backups/app-20260630-210620.db`.

## Важные выводы для эксплуатации

- Источником production-состояния теперь является БД в Docker volume нового VPS.
- Локальный fallback с тем же Telegram bot token должен быть остановлен, иначе появится Telegram polling conflict.
- `dashboard/config.local.toml` содержит SSH-пароль и не коммитится; в Git обновлен только `dashboard/config.example.toml` с новым IP.
- При переносе между VPS важно переносить не только image и `.env`, но и актуальную SQLite-БД, иначе потеряются черновики, tracking, outbox и сегодняшние пользовательские действия.

## Дневная группировка срочных и интеграционных заявок

Реализована логика дневных блоков для новых строк в листах `Срочные` и `Интеграции`.

- Новые одиночные заявки и новые массовые резервы вставляются в блок текущей даты формата `ДД.ММ.ГГ`.
- ADD/EDIT и CHIPS группируются отдельно внутри своих секций.
- Старые строки не перестраиваются автоматически.
- Если дневного разделителя нет, бот создаёт его при первой вставке дня.
- Дополнительно добавлен вспомогательный daily maintenance в `00:01` по `BOT_TIMEZONE`.
- Прошлый дневной блок получает Google dimension group, но строки не скрываются автоматически.
- Lazy-вставка разделителя при отправке заявки использует существующий section-lock и row-shift, чтобы не ломать координаты SQLite.
- Polling игнорирует строки-разделители и не считает их заявками.

Что учитывать дальше:

- [ ] После тестов проверить, удобно ли пользователям видеть серые строки-даты без автоскрытия.
- [ ] Не мигрировать старые строки без отдельного dry-run/backup сценария.
- [ ] При ручном удалении строки-даты бот восстановит блок только для новых строк, но не перенесёт старые заявки задним числом.

## Аудит дневной группировки перед production

Проведён отдельный технический анализ свежей логики дневных блоков с точки зрения оптимизации, гонок и нестандартных сценариев.

Вывод: базовая логика рабочая для MVP, но перед production-выкладкой нужно закрыть два риска.

- [ ] Защитить daily maintenance тем же section-lock, который используют одиночные заявки и массовые резервы, либо временно выключить `DAILY_SHEET_MAINTENANCE_ENABLED` и оставить только lazy-создание даты при первой заявке дня. Сейчас maintenance в `00:01` может вставлять строку даты параллельно с пользовательской вставкой в ту же секцию.
- [x] Вынести Google `addDimensionGroup` в best-effort операцию после успешной вставки даты/заявки/резерва. Группировка предыдущего дня больше не находится в одном `batchUpdate` с критичной вставкой; если Google отклонит группировку, заявка или массовый резерв всё равно остаются записанными.

Дополнительные риски и наблюдения:

- Если процесс упадёт между Google-вставкой и SQLite row-shift, координаты tracking могут устареть. Lock снижает риск гонок, но не делает Google+SQLite полностью атомарной операцией.
- Распознавание строки-даты строгое: `ДД.ММ.ГГ` в первой ячейке и пустые остальные ячейки. Если пользователь вручную допишет что-то в строку даты, бот может не распознать её и создать новый разделитель.
- Дневные блоки постепенно увеличивают размер листов. Polling их игнорирует логически, но Google read всё равно читает больше строк. Для роста нагрузки нужно будет уходить от лишних full scan.
- Maintenance ищет подходящие вкладки по названиям `Срочные`/`Интеграции` во всех настроенных spreadsheet. Если в production появятся архивные или тестовые вкладки с похожими именами, бот может создать дневный блок и там.
- Если пользователь вручную удалит строку даты, бот восстановит её для новых заявок, но не перенесёт старые строки задним числом.
- Если пользователь вручную вставит или удалит строки выше дневного блока, координаты SQLite могут устареть, если операция была сделана не через бота.

Рекомендуемые тесты перед production:

- [ ] Пользовательская вставка и daily maintenance одновременно в одной секции: maintenance не должен проходить без lock.
- [x] Ошибка `addDimensionGroup` не должна блокировать запись заявки.
- [ ] Повторная вставка в существующий дневной блок не создаёт второй разделитель той же даты.
- [ ] Срочные ADD/EDIT и срочные CHIPS создают разные дневные блоки.
- [ ] Интеграции создают дневной блок и не затрагивают старые строки без разделителей.
