# 09.07.2026 - обратная связь по CHIPS и связанному ADD

## Контекст

От пользователей пришла обратная связь по сценарию CHIPS:

> нужно, чтобы сценаристы могли одновременно добавить чипс и текст после чипса
>
> то есть сам текст кнопки + текст ответа, который идёт после кнопки
>
> Сейчас они добавляют ОТДЕЛЬНО текст чипса, причем должны указать с ним текст, который идёт после
>
> Наверное, может быть какая-то галочка "после чипса идёт новый текст", при нажатии которой текст добавится одновременно справа от чипса и в ADD

Эта обратная связь не сводится к простому добавлению нового поля. Пользователи описывают связку между CHIPS и ADD: чипс как кнопка и новый текст ответа, который должен открываться после выбора этой кнопки.

## Текущая реализация

Сейчас CHIPS является отдельным `change_type`.

Для одиночной CHIPS-заявки бот последовательно собирает:

1. Закрепленный сценарист.
2. Интент.
3. Причина.
4. Текст до чипса.
5. Текст чипса.
6. Текст после чипса.

В Google Sheets CHIPS записывается в отдельную CHIPS-схему:

| Колонка | Значение |
|---|---|
| A | Закрепленный сценарист |
| B | Статус |
| C | Причина |
| D | Текст до чипса |
| E | Текст чипса |
| F | Текст после чипса |
| G | Комментарий качества |
| H | Вопросы/комментарии редактора |
| I | Ответ сценариста |
| J | Редактор |
| K | Интент |
| L:U | технические поля |

Для CHIPS GigaChat не вызывается. Поле `Текст после чипса` уже существует и сохраняется отдельно от `Текст чипса`.

Однако это поле остается внутри CHIPS-заявки. Оно не создает отдельную ADD-заявку и не связывается с ADD-секцией.

## Что, вероятно, хотят пользователи

Пользователи описывают реальный сценарий:

1. Нужно добавить кнопку/чипс в сценарий.
2. У кнопки есть короткий текст, который видит клиент.
3. После нажатия на кнопку должен появиться новый полноценный текст ответа.

Пример:

- Текст кнопки/чипса: `Как подключить уведомления?`
- Текст ответа после нажатия: `Чтобы подключить уведомления, откройте настройки...`

Для сценариста это одна продуктовая правка: добавить чипс, который ведет к новому ответу. Но в текущей модели это может восприниматься как две разные сущности:

- CHIPS-заявка для самой кнопки;
- ADD-заявка для нового текста ответа.

Именно поэтому в обратной связи появляется формулировка:

> текст добавится одновременно справа от чипса и в ADD

То есть пользователи, вероятно, хотят, чтобы бот помогал не дублировать ручную работу: если после чипса появляется новый текст, этот текст должен быть отражен не только в CHIPS-строке, но и в обычной логике ADD.

## Почему текущая реализация не полностью закрывает потребность

Формально поле `Текст после чипса` уже есть. Но запрос пользователей не про наличие поля, а про смысловую связь:

- `Текст чипса` — это текст кнопки.
- `Текст после чипса` — это новый ответ, который появляется после нажатия на кнопку.
- ADD — это рабочий тип заявки для добавления нового текста.

Сейчас CHIPS и ADD существуют как независимые типы заявок. Между ними нет связи:

- у CHIPS нет связанной ADD-заявки;
- в dashboard CHIPS считается отдельной заявкой, а признак итогового ответа для CHIPS всегда `Нет`;
- уведомления и polling не рассматривают CHIPS как источник нового ADD-текста;
- массовые резервы CHIPS также регистрируются как CHIPS-строки, а не как связка CHIPS + ADD.

Поэтому сценарист может ощущать, что он уже ввел новый текст после чипса, но процесс ADD для этого текста отдельно не создан.

## Возможные варианты реализации

### Вариант 1. Быстрый UX-фикс без изменения модели данных

Оставить одну CHIPS-заявку, но уточнить формулировки:

- `Текст чипса` → `Текст кнопки / чипса`;
- `Текст после чипса` → `Текст ответа после нажатия на чипс`.

Дополнительно можно добавить вопрос:

> После чипса должен идти новый текст ответа?

Если пользователь выбирает `Да`, бот просит текст ответа после чипса. Если `Нет`, поле можно пропустить или заполнить служебным значением.

Плюсы:

- минимальные изменения;
- не ломает таблицы и dashboard;
- быстро снижает неоднозначность для сценаристов.

Минусы:

- не создается ADD-заявка;
- если процесс редакторов ожидает отдельный ADD, ручное дублирование может остаться.

### Вариант 2. CHIPS + автоматическое создание связанной ADD-заявки

Добавить режим:

> После чипса идет новый текст?

Если пользователь выбирает `Да`, бот создает две связанные заявки:

1. CHIPS-заявку: добавление кнопки/чипса.
2. ADD-заявку: добавление текста ответа после нажатия на чипс.

В CHIPS-строке текст ответа остается в колонке `Текст после чипса`, а в ADD-секции создается отдельная строка с этим же текстом как добавляемым ответом.

Плюсы:

- ближе всего к обратной связи пользователей;
- сценарист делает одну операцию вместо двух;
- редакторы видят новый текст в привычной ADD-логике.

Минусы и риски:

- нужно определить связь между двумя заявками;
- нужно избежать дублей при повторной отправке;
- нужно решить, отправлять ли одно или два уведомления редакторам;
- нужно решить, как это показывать в dashboard;
- нужно понять, нужна ли GigaChat-проверка для автоматически созданного ADD;
- нужно решить, как работает редактирование и удаление такой пары;
- нужно отдельно продумать массовые резервы.

### Вариант 3. Один новый тип workflow без отдельного ADD

Создать подтип CHIPS, например `CHIPS + новый ответ`, где таблица остается CHIPS-таблицей, но редактор понимает, что это не просто изменение кнопки, а добавление связанного ответа.

Плюсы:

- меньше технических рисков, чем у автоматического ADD;
- понятнее, чем текущая общая CHIPS-заявка.

Минусы:

- если редакторскому процессу нужен именно ADD, проблема не решается полностью;
- появится еще одна классификация внутри CHIPS.

## Что нужно уточнить у пользователей

Перед реализацией важно задать один ключевой вопрос:

> Когда вы говорите “текст добавится одновременно справа от чипса и в ADD”, вам нужно, чтобы бот создавал отдельную ADD-заявку для текста ответа, или достаточно, чтобы этот текст был явно заполнен в CHIPS-строке как “Ответ после нажатия на чипс”?

Дополнительные вопросы:

- Должен ли новый текст после чипса проходить обычную ADD-проверку через GigaChat?
- Должны ли редакторы видеть одну заявку или две связанные заявки?
- Если редактор меняет статус CHIPS, должен ли статус связанного ADD меняться автоматически?
- Если сценарист удаляет/отменяет CHIPS, нужно ли удалять связанный ADD?
- Нужно ли поддерживать этот сценарий в массовых заявках сразу или только в одиночных?
- Какой текст должен попадать в колонку `Суть изменений` для автоматически созданного ADD?
- Какой `Кейс или сообщения клиента` должен быть у связанного ADD: такой же, как у CHIPS, или отдельный?

## Предварительная рекомендация

Не стоит сразу делать автоматическое создание ADD без подтверждения процесса с редакторами. Это уже изменение бизнес-логики, а не просто улучшение формы.

Рациональный порядок:

1. Уточнить у пользователей, нужна ли именно отдельная ADD-заявка.
2. Если нет — сделать быстрый UX-фикс названий и подсказок CHIPS.
3. Если да — проектировать связанный workflow `CHIPS + ADD`, включая dashboard, уведомления, idempotency, удаление и массовые резервы.
