# 2026-06-29. Новая концепция массовых заявок

## Контекст

После обратной связи по текущему массовому workflow принято, что прежняя модель с отдельным листом `Массовый ввод`, отдельной структурой пачки, отдельным tracking пачки и последующим восстановлением перемещённых блоков слишком хрупкая.

Основная проблема текущего подхода: массовая заявка живёт как отдельная сущность внутри таблиц, но пользователи воспринимают строки как обычные заявки и могут переносить, удалять или смешивать их с одиночными. Из-за этого появляются ложные `not_found`, сложная логика восстановления, отдельные batch-состояния и риск рассинхронизации SQLite с Google Sheets.

## Новое продуктовое решение

Массовая заявка больше не должна быть отдельной бизнес-сущностью.

Новая модель:

- пользователь выбирает массовое заведение;
- выбирает направление;
- выбирает, куда заносить строки: `Срочные`, `Недельные`, `Интеграции`;
- выбирает тип строк: `ADD`, `EDIT` или `CHIPS`;
- указывает количество заявок;
- бот безопасно вставляет указанное количество строк в конец нужной секции;
- пользователь заполняет строки прямо в боевом листе;
- после нажатия `Заявка заполнена` бот регистрирует заполненные строки как обычные одиночные заявки.

После регистрации никакого отдельного batch-workflow нет: каждая заполненная строка становится обычной заявкой в `submitted_applications` и дальше обрабатывается теми же механизмами, что одиночная заявка.

## Важные решения

### 1. Статус до регистрации остаётся пустым

При создании резерва бот не ставит `Новая` и не проставляет другой рабочий статус.

Причина:

- редактор не должен видеть незаполненную строку как готовую заявку;
- фильтры по статусу не должны подхватывать черновики;
- резерв строк не должен попадать в работу до явной регистрации.

После успешной регистрации заполненных строк бот проставляет статус `Новая`.

### 2. Визуальное выделение только границами

Массовый резерв выделяется без изменения структуры таблицы:

- первая строка резерва получает толстую верхнюю границу;
- последняя строка резерва получает толстую нижнюю границу;
- заливка не используется;
- новые колонки не добавляются.

Это даёт визуальный ориентир, но не мешает фильтрам, статусам, цветам и существующей логике листов.

### 3. Незаполненные строки остаются резервом

Если пользователь запросил 20 строк, а заполнил 12:

- 12 заполненных строк регистрируются;
- 8 пустых строк остаются в таблице;
- пустые строки не получают `application_id`;
- пустые строки не получают статус;
- пустые строки не попадают в `submitted_applications`.

Технически после первой успешной регистрации массовая операция считается завершённой. Оставшиеся пустые строки остаются просто свободным резервом в листе. Если позже нужно завести ещё заявки, пользователь создаёт новую массовую операцию.

### 4. Понятие пачки упраздняется

Новые массовые заявки не должны создавать полноценный `batch` как бизнес-сущность.

Не нужно:

- отдельный dashboard по пачкам;
- отдельный polling пачек;
- архивный scan завершённых пачек;
- `batch_id` как обязательная связь новых заявок;
- восстановление перемещённой пачки;
- группировка строк пачки.

При этом на время незавершённого процесса всё равно нужна служебная запись в SQLite. Её лучше называть не `bulk_batch`, а `bulk_reservation`.

`bulk_reservation` нужна только для управления текущим процессом:

- кто создал резерв;
- куда вставлены строки;
- какой диапазон нужно читать при регистрации;
- сколько строк зарезервировано;
- какая кнопка Telegram должна завершить процесс.

После регистрации заявки живут независимо.

## Безопасная вставка строк

В этой версии должна быть не работа с заранее существующим пустым хвостом, а безопасная вставка строк в конец секции.

Правило:

- бот вставляет строки в конец выбранной секции;
- если ниже есть другие секции или заявки, их физические номера строк сдвигаются;
- после успешной вставки бот обязан пересчитать координаты всех отслеживаемых заявок ниже точки вставки.

Пересчёт координат нужен для `submitted_applications`:

- если `spreadsheet_id` совпадает;
- если `sheet_id` совпадает;
- если `last_seen_row_number >= insert_row`;
- тогда `last_seen_row_number += inserted_count`.

Это снижает риск ложных `not_found` после добавления массового резерва.

Важно: пересчёт должен выполняться только после успешного Google Sheets insert. Если Google API вернул ошибку, SQLite-координаты менять нельзя.

## Параллельное заведение массовых заявок

Параллельное создание должно поддерживаться.

Проблема: два пользователя могут одновременно выбрать один лист и одну секцию. Если оба одновременно прочитают структуру листа, они могут попытаться вставить строки в одно и то же место.

Решение: сериализация только на уровне целевой секции, а не всего бота.

Ключ lock:

```text
spreadsheet_id + sheet_id + section_kind
```

Примеры:

```text
ФЛ / Срочные / ADD
ФЛ / Срочные / CHIPS
ФЛ / 06.07 (1) / EDIT
ФЛ / Интеграции / ADD
```

Алгоритм:

1. Пользователь A подтверждает создание массового резерва.
2. Бот берёт lock на конкретную целевую секцию.
3. Бот заново читает структуру листа.
4. Бот вычисляет актуальную точку вставки.
5. Бот вставляет строки.
6. Бот пересчитывает SQLite-координаты заявок ниже вставки.
7. Бот сохраняет `bulk_reservation`.
8. Бот отдаёт ссылку пользователю A.
9. Lock освобождается.
10. Пользователь B, если он ждал ту же секцию, после освобождения lock заново читает уже обновлённый лист и получает следующий непересекающийся диапазон.

Пользовательский опыт:

- callback нужно подтверждать сразу;
- пользователю показывается сообщение `Готовлю строки...`;
- если lock ждётся дольше нескольких секунд, можно показать нейтральный текст: `Сейчас другой пользователь создаёт строки в этом же листе. Бот продолжит автоматически.`

Параллельные операции в разных секциях могут идти независимо.

## Регистрация заполненных строк

При нажатии `Заявка заполнена`:

1. Бот находит активный `bulk_reservation` пользователя.
2. Читает сохранённый диапазон.
3. Определяет полностью пустые строки.
4. Определяет заполненные строки.
5. Проверяет обязательные поля по типу `ADD`, `EDIT` или `CHIPS`.
6. Если есть частично заполненные строки, регистрация не выполняется.
7. Если ошибок нет, каждая заполненная строка получает:
   - `application_id`;
   - статус `Новая`;
   - технические поля одиночной заявки;
   - запись в `submitted_applications`;
   - dashboard projection;
   - уведомление, если это срочная заявка и для неё включены уведомления.

Пустые строки игнорируются и остаются в листе без статуса и технических полей.

## Ошибки и retry

Создание резерва должно быть идемпотентным:

- если Telegram callback повторился, бот не должен вставлять второй диапазон;
- если `bulk_reservation` уже создан, пользователь должен получить прежнюю ссылку;
- если Google insert не прошёл, SQLite-координаты не меняются.

Регистрация тоже должна быть идемпотентной:

- повторное нажатие не должно создавать дубли заявок;
- уже зарегистрированные строки должны распознаваться по техническим полям;
- частичный сбой Google/SQLite должен возвращать workflow в состояние, из которого можно безопасно повторить.

## Что остаётся открытым

- Нужно ли разрешать пользователю повторно использовать незаполненные строки старого резерва через бота или считать их обычным ручным резервом.
- Нужно ли применять LLM-проверку к массовым ADD/EDIT. Текущая рекомендация: на первом этапе не применять, чтобы не замедлять массовый ввод.
- Нужно ли отправлять редакторам одно агрегированное уведомление по срочному массовому вводу или отдельные уведомления по каждой зарегистрированной строке. Текущая рекомендация: одно агрегированное уведомление после регистрации.
- Нужно ли отдельное ограничение максимального количества строк, например 50, чтобы не создавать слишком большие пустые блоки.

## Предварительная рекомендация к реализации

Реализовывать по этапам:

1. Новая модель `bulk_reservation` без бизнес-понятия пачки.
2. Создание резерва в выбранной секции с lock на секцию.
3. Безопасная вставка строк и пересчёт координат tracking ниже вставки.
4. Регистрация заполненных строк как обычных одиночных заявок.
5. Толстые верхние и нижние границы для визуального выделения.
6. Очистка старого workflow `bulk_batches` только после подтверждения, что новая модель закрывает реальные сценарии.

Главный технический критерий: после массового заведения в системе не должно появляться новых особых сущностей, которые нужно отдельно polling-ить и восстанавливать. Массовый сценарий должен завершаться превращением заполненных строк в обычные заявки.

## Реализация первой версии

Начата реализация новой модели через SQLite-таблицу `bulk_reservations`.

Что внесено в код:

- добавлена сущность `BulkReservation` и состояния нового массового workflow;
- добавлена таблица `bulk_reservations` с автоматической миграцией при запуске;
- новый Telegram-flow: направление → место (`Срочные`, `Недельные`, `Интеграции`) → тип (`ADD`, `EDIT`, `CHIPS`) → количество строк → подтверждение;
- добавлен лимит `BULK_MAX_ROWS`, по умолчанию `50`;
- новый Google Sheets service вставляет пустой резерв строк в выбранную рабочую секцию и ставит толстые верхнюю/нижнюю границы;
- после вставки строк SQLite сдвигает координаты уже отслеживаемых заявок и активных резервов ниже точки вставки;
- регистрация резерва читает сохранённый диапазон, игнорирует пустые строки, блокирует частично заполненные строки и превращает заполненные строки в обычные одиночные заявки;
- новый массовый flow не создаёт `bulk_batches`, не заполняет `ID пачки` и не создаёт dashboard projection пачки;
- старый `bulk_batches` workflow оставлен для legacy callback `app:bulk_ready:<batch_id>`.

Ограничения текущей итерации:

- массовые ADD/EDIT пока не проходят GigaChat-проверку;
- агрегированное уведомление редакторам по срочному массовому вводу ещё нужно отдельно довести и протестировать;
- старые `bulk_batches` остаются в коде до отдельной cleanup-задачи;
- пустые строки после регистрации остаются ручным резервом и повторно ботом не подхватываются.

## Дополнительные наблюдения после локального прогона

Нужно починить синхронизацию дашборда под новую модель `bulk_reservations` и новые структуры рабочих таблиц. Сейчас риск в том, что dashboard projection может строиться из рабочей строки напрямую, а порядок колонок рабочего листа не совпадает с порядком колонок дашборда. Из-за этого в поле даты может попадать значение из другого поля, например `Кейс или сообщения клиента`. Правильное решение: для массовых строк строить dashboard row через отдельный dashboard builder, как для одиночных заявок, а не передавать worksheet-row как dashboard-row.

Нужно отдельно продумать визуальное выделение массового резерва в процессе заполнения. Толстые верхняя и нижняя границы помогают увидеть блок, но этого может быть недостаточно, если пользователь работает с широким листом и не видит все обязательные колонки.

Отдельная проблема — колонка `Интент` в массовых заявках. Сейчас она находится правее основных полей и может не попадать в видимую область экрана. Пользователь может не заметить, что её тоже нужно заполнить. Возможные варианты:

- дополнительно выделять цветом все колонки, которые пользователь обязан заполнить;
- использовать один цвет для обязательных пользовательских колонок и другой для технических/редакторских;
- добавить заметку или закреплённую подсказку рядом с резервом о том, какие поля обязательны;
- подумать, нужно ли для массового режима другое расположение `Интент`, если текущая схема создаёт регулярные ошибки заполнения.

Предварительная мысль: для массового режима стоит сделать визуальное выделение именно заполняемых колонок, а не только границ блока. Это снизит риск частично заполненных строк и повторных попыток регистрации.

## Реализованное уточнение по визуальному выделению

Внесено изменение в новый workflow `bulk_reservations`:

- при создании резерва больше не ставятся толстые верхняя и нижняя границы;
- обязательные пользовательские колонки подсвечиваются мягким светло-жёлтым цветом;
- для ADD/EDIT подсвечиваются сценарист, кейс, суть изменений, исходный текст и интент;
- для CHIPS подсвечиваются сценарист, причина, три текста чипса и интент;
- толстые границы теперь ставятся только после успешной регистрации заполненных строк;
- если в резерве остались пустые строки, границы охватывают только фактически зарегистрированный диапазон.

Смысл изменения: черновой резерв визуально показывает, что нужно заполнить, а толстые границы теперь означают уже зарегистрированный ботом блок.

## Реализованное исправление dashboard

Починено формирование dashboard projection для новой модели `bulk_reservations`.

Раньше при регистрации строк массового резерва в `dashboard_outbox` могла попадать сырая строка рабочего листа. У рабочего листа и общего дашборда разный порядок колонок, поэтому значения могли попадать не в свои поля.

Теперь для каждой зарегистрированной строки резерва строится отдельная строка дашборда в формате `DASHBOARD_HEADERS`: заявка отображается как обычная одиночная заявка, без `batch_id`, со статусом `Новая`, редактором `Редактор не выбран`, признаком итогового ответа `Нет` и ссылкой на конкретную рабочую строку.

## Аудит текущей реализации новой массовой модели

После первичного прохода по `bulk_reservations` выявлены пункты, которые стоит исправить до полноценного пилотного использования новой модели.

### Критично перед выкладкой

1. Повторное подтверждение создания резерва может создать второй диапазон строк.

   Сейчас `claim_bulk_reservation_creation()` возвращает reservation в состоянии `CREATING`, если создание уже началось и ещё не протухло. После этого `confirm_bulk_reservation_creation()` всё равно вызывает `create_reservation_with_lock()`. При двойном клике или параллельной обработке callbacks второй вызов может дождаться section-lock и вставить ещё один диапазон.

   Что сделать: если reservation уже `CREATING` и не протух, не запускать Google insert повторно. Возвращать пользователю сообщение в духе «строки уже создаются, подождите». Для retry использовать только stale `CREATING`.

2. Создание резерва не восстанавливается идемпотентно после сбоя между Google insert и записью координат в SQLite.

   Сейчас строки в Google вставляются пустыми, без `reservation_id` или другого маркера. Если процесс упадёт после успешного insert, но до `complete_bulk_reservation_creation()`, бот не сможет понять, что строки уже созданы, и при retry может вставить новый резерв.

   Что сделать: добавить невидимый или технически безопасный маркер резерва. Варианты: developer metadata Google Sheets, note на первой строке резерва или служебное значение в скрытой технической колонке. После этого retry сможет найти уже созданный диапазон и сохранить координаты без повторной вставки.

3. Сдвиг координат и сохранение координат резерва надо фиксировать одной SQLite-транзакцией.

   Сейчас после Google insert отдельно вызывается `shift_rows_after_insert()`, а затем отдельно `complete_bulk_reservation_creation()`. Если один шаг прошёл, а второй нет, локальные координаты могут временно стать несогласованными.

   Что сделать: добавить repository-метод, который в одной транзакции сохраняет координаты созданного резерва и сдвигает `submitted_applications`/активные `bulk_reservations` ниже точки вставки.

4. `FAILED` reservation сейчас считается активным.

   `get_active_bulk_reservation()` исключает только `REGISTERED` и `CANCELLED`. Значит неудачный резерв может блокировать пользователя и возвращать его в ошибочное состояние вместо создания новой массовой заявки.

   Что сделать: исключить `FAILED` из активных или добавить отдельное поведение: «повторить создание» / «создать заново» / «отменить».

### Важно для стабильности

5. Регистрация строк делает Google updates, tracking, dashboard outbox и завершение reservation отдельными шагами.

   Повторный запуск в основном идемпотентен, потому что `application_id` записывается в строку и dashboard projection upsert-ится по ID. Но локально возможны промежуточные состояния: часть tracking уже сохранена, часть dashboard outbox ещё нет, reservation ещё не `REGISTERED`.

   Что сделать: после Google updates сохранять tracking, dashboard projections, notification event и завершение reservation одной SQLite-транзакцией. Это снизит риск «половинчатой» локальной фиксации.

6. Параллельность защищена только in-process lock.

   Для одного контейнера это приемлемо, но при случайном запуске двух экземпляров бота или во время нестандартного деплоя два процесса не разделят один lock.

   Что сделать: добавить SQLite lease/lock по `spreadsheet_id + sheet_id + section_kind` или явно оставить это как ограничение эксплуатации: строго один процесс бота.

7. Пустые строки после регистрации остаются подсвеченным резервом, но бот повторно их не регистрирует.

   Это может сбивать пользователя: визуально строки выглядят как область для заполнения, но кнопка «Заявка заполнена» после регистрации уже ведёт к завершённому состоянию.

   Что сделать: выбрать продуктовую логику. Вариант A: после регистрации очищать подсветку у неиспользованных строк и считать их ручным резервом. Вариант B: оставить reservation частично открытым и разрешить регистрировать оставшиеся строки позднее. Вариант A проще и безопаснее для первой версии.

8. Клавиатура выбора типа показывает `CHIPS` для интеграций, хотя flow потом отклоняет этот выбор.

   Это рабочий, но не лучший UX: пользователь видит доступную кнопку, нажимает и получает отказ.

   Что сделать: для `target_kind=integration` показывать только ADD/EDIT или сделать отдельную клавиатуру с учётом выбранного места.

   Это лучше, чем пустое значение, но для редакторов и мониторинга менее удобно.

## Реализованные исправления по аудиту bulk reservations

Внесён набор стабилизационных исправлений перед выкладкой новой массовой модели:

- повторное подтверждение, пока reservation находится в свежем состоянии `CREATING`, больше не запускает повторную вставку строк;
- для созданного резерва в Google Sheets добавляется `developerMetadata` с `reservation_id`, поэтому retry после сбоя между Google insert и SQLite-фиксацией может найти уже созданный диапазон;
- сохранение координат нового резерва и сдвиг координат нижележащих заявок/резервов выполняются одной SQLite-транзакцией;
- `FAILED` reservation больше не считается активным и не блокирует пользователя при старте новой массовой заявки;
- регистрация заполненных строк теперь сохраняет tracking, dashboard projections, уведомление редакторам и состояние `REGISTERED` одной SQLite-транзакцией;
- добавлен SQLite section-lock поверх in-process lock, чтобы случайный второй процесс не вставлял строки в ту же секцию параллельно;
- после успешной регистрации подсветка обязательных колонок очищается у пустых незарегистрированных строк резерва;
- для интеграций в выборе типа изменения больше не показывается `CHIPS`;
- добавлены regression-тесты на повторное подтверждение `CREATING`, восстановление по Google metadata, атомарный сдвиг координат, `FAILED` reservation, section-lock, скрытие `CHIPS` для интеграций и очистку подсветки пустых строк.

Оставшееся продуктовое решение: что делать с пустыми строками после частичной регистрации в долгосрочной логике. Сейчас они остаются как ручной резерв и визуально больше не подсвечиваются как активная зона бота.

## Повторный аудит после стабилизационных исправлений

После внесённых исправлений новая модель `bulk_reservations` стала заметно безопаснее: закрыты основные риски двойного создания резерва, локально атомарной фиксации координат, блокировки `FAILED`-состоянием и некорректной dashboard-проекции. Полный прогон тестов после этих изменений был зелёным.

Оставшиеся пункты, которые стоит сделать следующими.

### Важно до широкого использования

1. Уточнить поведение восстановления по Google `developerMetadata`.

   Сейчас `developerMetadata` используется как маркер уже созданного резерва после сбоя между Google insert и записью координат в SQLite. Это правильное направление, но текущая логика безопасно работает только если поиск metadata выполнился успешно. Если сам metadata-search временно упадёт из-за Google API, есть риск, что бот не найдёт уже вставленные строки и при повторе создаст новый резерв.

   Что лучше сделать: различать “metadata API недоступен в тестовом fake-клиенте” и реальную ошибку Google API. В production при ошибке metadata-search лучше fail-closed: не вставлять новые строки, а вернуть retry-сообщение. Это безопаснее, чем потенциально создать второй резерв.

2. Использовать `developerMetadata` не только при создании, но и при регистрации резерва.

   Сейчас регистрация читает сохранённые `start_row/end_row`. Если пользователь вручную вставит или удалит строки выше резерва, координаты могут устареть. Для одиночных заявок и старых пачек уже была похожая категория проблем с перемещениями.

   Что лучше сделать: перед регистрацией искать актуальный range по `reservation_id` через metadata. Если range найден и отличается от SQLite, обновлять координаты и читать актуальный диапазон. Это уменьшит поломки от ручных изменений в листе.

3. Сократить количество Google API вызовов при регистрации массового резерва.

   Сейчас каждая зарегистрированная строка обновляется отдельным `batchUpdate`, а потом отдельно ставятся границы и очищается подсветка пустых строк. Для 30-50 строк это может давать лишнюю нагрузку и повышать шанс 429/quota.

   Что лучше сделать: собирать все `updateCells` по строкам, границы и очистку подсветки в один общий `spreadsheets.batchUpdate` или в минимальное число batch-запросов. Это особенно важно перед нагрузкой 15+ пользователей.

4. Явно объяснить пользователю судьбу пустых строк резерва.

   Текущая логика: пустые строки после регистрации остаются в листе как ручной резерв и бот потом их не регистрирует. Подсветка с них очищается, но продуктово это всё равно может быть неочевидно.

   Что лучше сделать: в сообщении перед кнопкой `Заявка заполнена` и в итоговом сообщении явно писать: “пустые строки останутся в таблице, но бот их уже не зарегистрирует в рамках этой массовой заявки”. Если нужен другой сценарий, его надо проектировать отдельно.

### Желательно после первой выкладки

5. Добавить нагрузочный профиль именно для нового `bulk_reservations`.

   Старые loadtest-сценарии не полностью отражают новую механику: безопасная вставка строк в боевые секции, подсветка обязательных колонок, регистрация как одиночных заявок, агрегированное уведомление редакторам.

   Что лучше сделать: добавить профиль, который создаёт несколько параллельных reservations в одну секцию и в разные секции, затем регистрирует частично заполненные и полностью заполненные диапазоны. Отдельно проверить число Google API вызовов и поведение при 429.

6. Усилить observability по массовым резервам.

   Сейчас для эксплуатации будет полезно видеть не только ошибки, но и жизненный цикл резерва: создан, вставлен в Google, зарегистрирован, сколько строк заполнено, сколько пустых, сколько заняла блокировка секции.

   Что лучше сделать: добавить структурные логи с `reservation_id`, `telegram_user_id`, `target_kind`, `change_type`, `sheet_name`, `start_row/end_row`, `registered_count`, временем ожидания lock и временем Google API операций.

7. Защитить технические колонки от ручного заполнения.

   В новой массовой модели строки создаются прямо в боевых листах. Даже при подсветке обязательных колонок пользователь может случайно писать в технические поля.

   Что лучше сделать: минимум — визуально отделить техническую часть и не подсвечивать её; лучше — добавить protected range или warning/validation для технических колонок, если это не будет мешать редакторам.

8. Улучшить автора в dashboard для массовых строк.

   Сейчас для массовых строк автор может быть техническим `Telegram <id>`. Это лучше, чем пусто, но хуже для мониторинга.

   Что лучше сделать: сохранять display name пользователя при создании reservation или брать дефолтного закреплённого сценариста, если он однозначно выбран.

9. Отдельно решить вопрос LLM-проверки для массовых ADD/EDIT.

   Сейчас массовые ADD/EDIT не проходят GigaChat-проверку. Это снижает нагрузку и упрощает регистрацию, но повышает риск массового внесения неполных требований.

   Что лучше сделать: после стабилизации механики решить продуктово, нужна ли проверка массовых строк. Если нужна, лучше запускать её на этапе регистрации и возвращать список проблемных строк, а не проверять каждую строку во время заполнения.

### Технический долг

10. Изолировать legacy `bulk_batches`.

    Старый workflow оставлен для совместимости со старыми сообщениями и данными. Это правильно для мягкой миграции, но увеличивает сложность кода.

    Что лучше сделать: после подтверждения новой модели на пилоте составить отдельный cleanup-план: отключить старый UI уже сделано, затем удалить или заморозить legacy-регистрацию, polling старых пачек и старые таблицы только после проверки, что активных старых пачек больше нет.

11. Сделать TTL section-lock настраиваемым.

    Сейчас lease для SQLite section-lock зафиксирован в коде. Для одного контейнера это нормально, но при эксплуатационных проблемах удобнее иметь настройку.

    Что лучше сделать: добавить env-параметр вроде `BULK_SECTION_LOCK_TTL_SECONDS=600` и описать его в README.

Рекомендуемый порядок: сначала fail-closed для metadata-search и поиск актуального metadata-range при регистрации, затем batching Google updates, затем нагрузочный профиль и эксплуатационные логи. Остальное можно делать после первой контролируемой выкладки новой массовой модели.
