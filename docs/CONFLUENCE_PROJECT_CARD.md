# Карточка Проекта: Alfa Auto Requests Bot

## Дата Запуска

**17.06.2026** — первый запуск Telegram-бота для пилотной группы.

Текущий статус: активный пилот. Данные ниже относятся к production-срезу от 13.07.2026 и должны обновляться при подготовке следующего статуса проекта.

## Описание Проекта

### Какую Проблему Решает

До запуска бота сценаристы передавали заявки на изменения в свободном формате и дополнительно вручную искали редактора, проверяли таблицы и уточняли, замечена ли заявка. Это создавало неоднородные описания, лишние уточнения и слабую прозрачность состояния работы.

Бот переводит заведение заявки в единый пошаговый сценарий: собирает обязательные данные, записывает их в нужный рабочий лист Google Sheets, возвращает ID заявки и отслеживает её дальнейший статус. Редактор продолжает работать в привычной Google-таблице.

### Как Работает AI

Для одиночных заявок ADD/EDIT GigaChat выполняет вспомогательную проверку практической полноты описания. В проверку передаются интент, кейс или сообщения клиента, суть изменений и уточнение пользователя. Если не хватает существенной информации, бот задаёт одно конкретное уточнение; заявка не блокируется навсегда и после уточнения продолжает путь в таблицу.

AI не принимает редакторское решение и не изменяет текст заявки автоматически. Для CHIPS и новых массовых заявок GigaChat не вызывается.

### Где Используется

- Сценаристы создают одиночные и массовые заявки в Telegram.
- Редакторы обрабатывают заявки, меняют статусы и оставляют комментарии в Google Sheets.
- Руководители и координаторы используют read-only дашборд для обзора потока заявок.
- Текущий подтверждённый production-срез относится к направлению ФЛ; сценарии включают раскатки, срочные заявки, интеграции и CHIPS.

## Используемые Технологии

- Python 3.12 и `aiogram 3` для Telegram-бота.
- Google Sheets API и `google-api-python-client` для записи, чтения статусов и форматирования рабочих листов.
- GigaChat API для вспомогательной проверки полноты одиночных ADD/EDIT-заявок.
- SQLite для черновиков, tracking, идемпотентности и durable outbox очередей.
- Docker Compose для сборки и запуска на VPS.
- Google Sheets как источник правды по рабочим заявкам; read-only дашборд синхронизируется отдельно.

## Влияние Проекта

### Тип Влияния

| Тип | Влияние |
|---|---|
| Внутренние процессы | Прямое: единый формат заявок, автоматическая маршрутизация в рабочие листы, прозрачное отслеживание статусов и уведомления. |
| Клиенты | Косвенное: более структурированная постановка и ускорение взаимодействия сценариста с редактором должны повышать качество и скорость изменений клиентских сценариев. Экономический и клиентский эффект пока не подтверждён отдельным исследованием. |

### Описание Эффекта

- Сценарист получает подтверждение записи и ID заявки сразу после отправки.
- При статусе `В работе` и последующих важных изменениях автор получает уведомление, поэтому реже требуется вручную проверять таблицу или тегать редактора.
- Единые подсказки разделяют контекст кейса и суть изменения; это снижает риск неоднозначных заявок и лишних уточнений.
- Редактор получает структурированную строку в привычной таблице, без переключения на новый интерфейс для основной работы.

Качественная обратная связь пилота подтверждает полезность уведомлений и снижение числа вопросов по сути изменений. При этом ускорение полного процесса и клиентский эффект требуют дальнейшего измерения.

## Метрики Проекта

**Источник:** read-only production-срез SQLite и технических очередей от 13.07.2026.  
**Период:** последние 30 дней на момент среза.

| Метрика | Значение | Почему можно использовать |
|---|---:|---|
| Пользователи пилота | 10 | Фактические авторы заявок в production. |
| Создано заявок | 128 | Фактические tracking-записи за 30 дней. |
| Возврат в другой день | 9 из 10 пользователей | Показывает повторное использование, а не единичный тест. |
| Возврат в другую неделю | 8 из 10 пользователей | Показывает устойчивость использования. |
| Медианное время создания | 1 мин 28 с, `n=17` | Первая точная выборка событий «черновик → отправка»; показатель предварительный из-за размера выборки. |
| Срочные заявки | 29 из 128 (22,7%) | Подтверждает использование в приоритетном сценарии. |
| Массовые заявки | 36 из 128 (28,1%) | Подтверждает потребность в пакетном заведении. |
| Потерянные заявки на срезе | 0 | Техническая надёжность tracking на момент среза. |
| Доставка уведомлений | 43 из 43 `SENT`, 0 `FAILED`, 0 retry | Состояние durable notification outbox на момент среза. |

Не использовать как доказанный KPI полного цикла: время до первого действия редактора и время до финального ответа пока имеют небольшую и неоднородную выборку. Экономию времени и SLA следует считать после накопления сопоставимых данных.

## Архитектура Решения

```text
Сценарист / редактор
        |
        v
Telegram-бот (Python + aiogram)
        |
        +--> GigaChat API
        |    Проверка полноты только для одиночных ADD/EDIT
        |
        +--> Google Sheets API
        |    Рабочие таблицы, статусы, комментарии, итоговые ответы
        |
        +--> SQLite
             Черновики, tracking, section-lock, outbox, идемпотентность

Фоновый polling Google Sheets
        |
        +--> Telegram-уведомления автору и редакторам
        +--> Read-only дашборд
```

Рабочие Google Sheets являются источником правды по содержанию и статусам заявок. SQLite хранит техническое состояние, координаты строк и очереди; outbox отделяет успешное создание заявки от временных ошибок Telegram или дашборда.
