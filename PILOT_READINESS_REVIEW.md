# Готовность Бота К Пилоту На 5 Пользователей

Дата аудита: 10 июня 2026 года.

## 1. Итоговый Вывод

Текущая версия функционально подходит для контролируемой демонстрации и покрыта 133 автоматическими тестами. Нагрузка от пяти пользователей сама по себе не является проблемой: один процесс Python, SQLite и Telegram polling способны обслуживать такой объем.

Основные риски пилота связаны не с производительностью, а с целостностью данных и восстановлением после ошибок:

- параллельное создание и подтверждение массовых заявок;
- повторное нажатие кнопок отправки;
- частичный сбой между Google Sheets и SQLite;
- рост количества Google Sheets API запросов по мере накопления заявок;
- отсутствие автоматического резервного копирования базы;
- отсутствие healthcheck и уведомлений администратору о постоянных ошибках;
- секреты присутствуют в локальном deploy-архиве.

Запуск без исправлений возможен только как короткая демонстрация под постоянным наблюдением администратора. Для пилота на несколько дней или недель нужно выполнить блок `P0`.

## 2. Текущая Модель Выполнения

В проекте нет отдельной очереди задач.

- `aiogram` получает Telegram-события через polling.
- Обработчики разных пользователей могут выполняться параллельно.
- Вызовы Google Sheets выполняются в фоновых потоках через `asyncio.to_thread`.
- Проверка статусов работает одной фоновой coroutine с интервалом, по умолчанию, 30 секунд.
- Обновление дашборда ограничивается отдельным интервалом, по умолчанию, 300 секунд.
- Состояние хранится в одном SQLite-файле в Docker volume.
- Защита одиночных записей в один лист есть только внутри одного процесса.
- Полноценной блокировки массовых заявок и долговечной очереди повторных попыток нет.

Проект должен работать только в одном экземпляре контейнера. Запуск второго экземпляра приведет к конкурирующему Telegram polling, дублированию фоновых проверок и конфликтам SQLite/Google Sheets.

## 3. Оценка Вместимости

### Пять Пользователей

После исправления критических проблем система должна без труда выдерживать:

- пять одновременно активных пользователей;
- несколько одиночных заявок в минуту;
- массовые заявки на десятки строк;
- одного или нескольких редакторов, меняющих данные в Google Sheets.

Ограничивающим фактором будет Google Sheets API, а не CPU.

### VPS

Минимально допустимо:

- 1 vCPU;
- 1 ГБ RAM;
- 15 ГБ SSD;
- swap не менее 1 ГБ.

Рекомендуется для пилота:

- 1-2 vCPU;
- 2 ГБ RAM;
- 20 ГБ SSD;
- сборка Docker-образа вне VPS или при остановленном старом контейнере;
- ротация Docker-логов.

Существующего VPS с 1 CPU и 1 ГБ RAM достаточно, если на нем не выполняются тяжелые параллельные сборки и настроена ротация логов. Запас в 2 ГБ RAM снизит риск OOM во время сборки, тестов и одновременной работы SDK.

## 4. P0: Обязательно Исправить До Пилота

### 4.1 Защитить Границы Массовых Заявок

Сейчас подтверждение массовой заявки читает до 1000 строк вниз от начала ее секции. Надежная граница текущей секции не определяется.

Риск:

- ниже может уже находиться следующая массовая заявка;
- ее строки могут быть зарегистрированы как часть предыдущей пачки;
- ID, автор и tracking будут привязаны к неправильной пачке.

Что сделать:

1. Хранить в `bulk_batches` фактический `data_end_row`.
2. При создании следующей пачки закрывать диапазон предыдущей.
3. При регистрации читать только строки между заголовком текущей пачки и заголовком следующей.
4. Явно распознавать служебную строку `Пачка BATCH-*` и прекращать сканирование перед ней.
5. Запретить регистрацию строк, находящихся за пределами секции.
6. Добавить тест с двумя пачками на одном листе, где подтверждается первая.

Временное ограничение, если исправление не готово: разрешать только одну незавершенную массовую заявку на один лист направления.

### 4.2 Добавить Блокировки Массового Режима

Создание и регистрация массовых заявок сейчас не защищены от параллельного выполнения.

Возможные сценарии:

- два пользователя одновременно вычисляют одинаковую стартовую строку;
- один пользователь дважды нажимает `Заявка заполнена`;
- два обработчика видят пустой ID и записывают разные ID в одну строку;
- группировка строк создается повторно.

Что сделать:

- блокировка создания пачки по ключу `(spreadsheet_id, sheet_name)`;
- блокировка регистрации по `batch_id`;
- состояние пачки: `DRAFT`, `REGISTERING`, `REGISTERED`;
- атомарный переход `DRAFT -> REGISTERING`;
- повторное подтверждение зарегистрированной пачки должно возвращать прежний результат;
- кнопка должна становиться логически неактивной после успешной регистрации;
- добавить конкурентные тесты с `asyncio.gather`.

### 4.3 Сделать Отправку Одиночной Заявки Идемпотентной

При двойном нажатии `Отправить` одна и та же заявка может быть добавлена в Google Sheets повторно. Блокировка листа сериализует запросы, но не предотвращает повторную вставку.

Также возможен сценарий:

1. строка успешно записалась в Google Sheets;
2. сохранение tracking в SQLite завершилось ошибкой;
3. пользователь повторяет отправку;
4. появляется вторая строка с тем же ID.

Что сделать:

- хранить статус отправки `PENDING`, `SENT`, `FAILED`;
- перед append искать `application_id` в целевом листе;
- не добавлять строку, если ID уже существует;
- блокировать submit по `telegram_user_id` или `application_id`;
- после найденной существующей строки восстанавливать SQLite tracking;
- добавить тест двойного нажатия и тест сбоя после Google Sheets append.

### 4.4 Исправить Google API Retry И Клиенты

Внешние ошибки `429`, `5xx`, timeout, `Broken pipe`, reset соединения и временные DNS/TLS ошибки неизбежны.

Сейчас обработка неоднородна:

- часть ошибок возвращается пользователю;
- polling повторяется только на следующем полном цикле;
- dashboard rate-limit частично обрабатывается;
- общего retry-механизма нет;
- один Google API client переиспользуется из разных потоков.

Google API client на базе `httplib2` не следует считать потокобезопасным.

Что сделать:

- единая обертка Google API вызовов;
- retry только для временных ошибок: `429`, `500`, `502`, `503`, `504`, timeout, connection reset, broken pipe;
- exponential backoff с jitter, например 1, 2, 4, 8 секунд;
- ограничение числа попыток;
- пересоздание клиента после сетевой ошибки;
- отдельный client на поток/операцию либо последовательный Google API executor;
- отсутствие retry для ошибок схемы, доступа `403` и неверных данных;
- понятный `operation_id` в логах.

### 4.5 Снизить Google Sheets API Нагрузку Polling

Массовые заявки читаются поштучно. Каждая пачка добавляет постоянные запросы на каждом цикле, включая уже завершенные пачки.

При интервале 30 секунд одна пачка может создавать несколько чтений в минуту. После накопления десятков пачек сервис снова приблизится к лимиту `ReadRequestsPerMinutePerUser`.

Дополнительный риск: при обновлении дашборда выполняются отдельные read/upsert операции для большого числа tracked-заявок.

Что сделать:

- читать только активные пачки;
- прекращать polling строк пачки после статуса `Готова`, кроме редкой контрольной проверки;
- добавить `tracking_active` или `completed_at`;
- объединять чтения диапазонов через `values.batchGet`;
- группировать пачки одного листа в один запрос;
- синхронизировать дашборд пакетно: одно чтение и один `batchUpdate` за цикл;
- добавить счетчики Google API запросов на цикл;
- ввести защиту: если получен `429`, увеличить паузу следующего цикла.

### 4.6 Настроить SQLite Для Параллельной Работы

Каждая repository-операция открывает новое соединение. WAL и `busy_timeout` явно не настроены.

При одновременной записи flow, регистрации пачки и status polling возможны ошибки `database is locked`.

Что сделать:

```sql
PRAGMA journal_mode=WAL;
PRAGMA busy_timeout=10000;
PRAGMA foreign_keys=ON;
PRAGMA synchronous=NORMAL;
```

Дополнительно:

- объединять связанные изменения в транзакции;
- добавить индексы по `submitted_applications.batch_id`, `telegram_user_id`, `sheet_name`;
- индекс по активным bulk-пачкам;
- логировать длительность SQLite операций;
- добавить конкурентный тест нескольких writers.

### 4.7 Настроить Резервное Копирование И Восстановление

Docker volume переживает перезапуск, но не защищает от удаления volume, повреждения диска или ошибочного деплоя.

Нужно:

- ежедневный backup SQLite через SQLite backup API или `.backup`, а не простое копирование активного файла;
- хранить минимум семь ежедневных копий;
- копировать backup вне Docker volume;
- еженедельно проверять восстановление в тестовый файл;
- перед каждым deploy создавать backup;
- документировать команду восстановления;
- не выполнять `docker compose down -v`.

Для Google Sheets желательно включить историю версий и ограничить права удаления вкладок.

### 4.8 Удалить И Ротировать Секреты

В текущем workspace присутствуют `.env` и `credentials.json`. Они исключены через `.gitignore` и `.dockerignore`, но файл `deploy.tar.gz` содержит оба секрета.

Это критический риск.

Нужно до пилота:

1. Считать секреты из архива скомпрометированными.
2. Перевыпустить Telegram token, GigaChat credentials и Google service account key, если архив передавался или хранился вне доверенного VPS.
3. Удалить `deploy.tar.gz` и старые копии.
4. Генерировать deploy-архив только по allowlist файлов.
5. Хранить `.env` и Google key только на VPS с правами `600`.
6. Не переносить секреты через мессенджеры.
7. Добавить secret scanning в CI.

### 4.9 Добавить Healthcheck И Контроль Фоновой Задачи

Контейнер считается работающим, даже если status polling постоянно падает. Docker видит живой Python-процесс, но уведомления и дашборд могут не работать.

Что сделать:

- heartbeat status polling в SQLite или отдельном файле;
- timestamp последнего успешного Telegram poll;
- timestamp последнего успешного чтения Google Sheets;
- Docker healthcheck, проверяющий свежесть heartbeat;
- предупреждение администратору после нескольких последовательных ошибок;
- счетчик consecutive failures;
- отдельное лог-сообщение о восстановлении после ошибки.

### 4.10 Настроить Ротацию Логов

В compose нет ограничений Docker logging driver. На VPS с диском 15 ГБ длительные traceback и HTTP-логи могут заполнить диск.

Добавить:

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "5"
```

Также:

- убрать постоянный INFO-лог полного raw-ответа GigaChat;
- включать raw response только отдельным debug-флагом;
- не писать пользовательский текст и секреты в production-логи;
- добавить request/application/batch ID в структурированные логи.

## 5. P1: Желательно Исправить В Первую Неделю Пилота

### 5.1 Изолировать Ошибки Уведомлений По Пользователям

Сейчас ошибка отправки одному пользователю может прервать обработку остальных пользователей в текущем polling-цикле.

Нужно:

- отправлять уведомления каждому пользователю в отдельном `try/except`;
- не обновлять tracking только для неотправленного уведомления;
- продолжать обработку остальных пользователей;
- отдельно обрабатывать Telegram `Forbidden`/blocked bot;
- после нескольких permanent-ошибок отключать доставку этому получателю и уведомлять администратора.

### 5.2 Исправить Агрегацию Поля «Итоговый Ответ Есть» Для Пачки

Во время polling дашборд может обновляться по одной строке пачки. Значение `final_answer_present=bool(current.final_answer)` отражает только текущую строку, а не всю пачку.

Риск: строка без ответа может перезаписать `Да` на `Нет`, хотя в другой строке пачки ответ уже есть.

Нужно рассчитывать агрегат по всем строкам пачки за один цикл.

### 5.3 Добавить Preflight При Запуске

До старта Telegram polling проверить:

- наличие всех обязательных spreadsheet ID;
- существование credentials-файла;
- права service account на таблицы;
- доступность dashboard;
- существование prompt-файлов;
- корректность proxy;
- возможность открыть SQLite на запись;
- наличие свободного места на диске.

Ошибки конфигурации должны останавливать запуск до приема пользовательских заявок.

Отсутствие GigaChat credentials можно оставить допустимым только при явном флаге `LLM_FALLBACK_ALLOWED=true`.

### 5.4 Защитить Google Sheets От Ручного Повреждения

Служебные колонки и строки могут быть случайно изменены пользователями.

Рекомендуется:

- защитить ID, Telegram ID, batch ID и служебные колонки;
- разрешить сценаристу редактировать только пользовательский диапазон;
- разрешить редакторам менять статус, редактора, комментарий и итоговый ответ;
- закрепить строки заголовков;
- добавить примечания к служебным колонкам;
- проверять уникальность ID при polling;
- логировать перемещение или исчезновение tracked-заявки.

### 5.5 Добавить Операторские Команды

Минимальный набор:

- `/health` только для администратора;
- `/my_active` для пользователя;
- `/retry_dashboard`;
- `/retry_tracking`;
- команда проверки пачки по ID;
- команда повторного формирования ссылки;
- команда отключения/включения polling.

### 5.6 Синхронизировать Зависимости

Сейчас `requirements.txt` и `pyproject.toml` расходятся: в `pyproject.toml` указан `openpyxl`, хотя текущий массовый flow больше не использует xlsx.

Нужно:

- оставить один источник зависимостей;
- зафиксировать точные версии lock-файлом;
- использовать один и тот же lock локально, в CI и Docker;
- включить автоматическую проверку уязвимостей.

### 5.7 Нормализовать Деплой И Rollback

В текущем workspace не обнаружен активный Git-репозиторий, а основной deploy-архив содержит секреты.

Для пилота нужно:

- Git-репозиторий;
- immutable Docker image с тегом commit SHA;
- CI: compile, unit tests, Docker tests;
- deploy только успешного image;
- backup SQLite перед deploy;
- healthcheck после deploy;
- автоматический rollback на предыдущий image;
- хранение последних 5-10 образов.

## 7. Обязательные Тесты Перед Пилотом

### Конкурентность

1. Пять пользователей одновременно создают одиночные заявки в один лист.
2. Один пользователь дважды нажимает `Отправить`.
3. Два пользователя одновременно создают массовые заявки одного направления.
4. Один пользователь дважды нажимает `Заявка заполнена`.
5. Первая пачка подтверждается после создания второй.
6. Редактор меняет статусы во время регистрации пачки.

### Сбои

1. Google возвращает `429`.
2. Google возвращает `503`.
3. Возникает `Broken pipe` после отправки запроса.
4. Контейнер перезапускается после записи в Google, но до записи в SQLite.
5. Контейнер перезапускается во время массовой регистрации.
6. Telegram недоступен, затем восстанавливается.
7. GigaChat недоступен.
8. SQLite временно занят другим writer.

### Данные

1. В таблице перемещают строки.
2. В таблице сортируют заявки.
3. Удаляют tracked-строку.
4. Дублируют ID вручную.
5. Меняют заголовок колонки.
6. Вставляют строку между шапкой пачки и ее данными.
7. Массовая заявка содержит 1, 10, 50 и 100 строк.
8. В комментариях и текстах есть HTML, emoji и длинные значения.

### Восстановление

1. Восстановить SQLite из backup.
2. Откатить Docker image.
3. Проверить, что старый image читает существующую базу или заранее блокировать несовместимый rollback.
4. После восстановления выполнить reconciliation tracking.

## 8. Ограничения На Период Пилота

Пока P0 не реализован полностью:

- запускать только один контейнер;
- не создавать одновременно несколько незавершенных массовых заявок в одном направлении;
- не нажимать кнопки отправки повторно, пока бот не ответил;
- не удалять строки и вкладки;
- не переименовывать колонки;
- назначить одного технического администратора;
- ежедневно проверять логи, свободное место и backup;
- вести отдельный список инцидентов с ID заявки/пачки и временем;
- иметь ручной способ добавить пропущенную строку в tracking.

## 9. Наблюдаемость Пилота

Минимальные показатели:

- бот доступен;
- время последнего успешного status polling;
- число polling-ошибок подряд;
- количество Google API запросов;
- количество `429`, timeout и connection errors;
- число неотправленных уведомлений;
- размер SQLite;
- свободное место VPS;
- память контейнера;
- количество активных черновиков;
- количество активных массовых заявок;
- среднее время отправки одиночной заявки;
- среднее время регистрации пачки.

Критические алерты:

- polling неуспешен более 5 минут;
- контейнер перезапустился более трех раз за 15 минут;
- свободно менее 2 ГБ;
- backup старше 24 часов;
- обнаружены дубли ID;
- Google API возвращает `429` несколько циклов подряд;
- SQLite сообщает `database is locked` или corruption.

## 10. Рекомендуемый План Работ

### Этап 1. До Пилота

1. Ротация секретов и удаление небезопасного архива.
2. Границы и блокировки массовых заявок.
3. Идемпотентность одиночной отправки.
4. Google retry и безопасная работа клиентов.
5. WAL, busy timeout и backup SQLite.
6. Ограничение polling только активными данными.
7. Healthcheck, лог-ротация и базовые алерты.
8. Конкурентные и recovery-тесты.

### Этап 2. Первые Два Дня

- один администратор наблюдает логи;
- не более двух пользователей одновременно;
- одна массовая заявка на направление;
- ежедневная сверка SQLite, рабочих таблиц и дашборда;
- фиксация всех ошибок с точным временем.

### Этап 3. Полный Пилот

- подключить всех пять пользователей;
- разрешить параллельные одиночные заявки;
- массовые заявки запускать после успешного concurrency-теста;
- раз в день формировать отчет: заявки, ошибки, задержки, ручные исправления.

### Этап 4. Завершение Пилота

- проверить отсутствие потерянных и дублированных заявок;
- сравнить рабочие таблицы с дашбордом;
- проверить доставку уведомлений;
- собрать обратную связь;
- принять решение о PostgreSQL, отдельном worker и промышленном мониторинге.

## 11. Критерии Готовности

Пилот можно считать технически готовым, если:

- секреты перевыпущены и не входят в deploy-артефакты;
- есть успешный backup и проверенное восстановление;
- двойное нажатие не создает дубли;
- две массовые заявки не пересекаются;
- подтверждение пачки обрабатывает только ее строки;
- временный сбой Google автоматически повторяется;
- завершенные пачки не создают постоянную polling-нагрузку;
- `429` не выводит систему из рабочего состояния;
- один проблемный пользователь не блокирует уведомления остальных;
- Docker healthcheck отражает состояние фонового polling;
- логи не могут заполнить диск;
- deploy имеет рабочий rollback;
- пройдены сценарии с пятью параллельными пользователями.

## 12. Приоритетный Вывод

Для пилота на пять человек не требуется усложнять инфраструктуру Kubernetes, Redis или отдельной высоконагруженной БД. Нужны более базовые гарантии:

1. одна операция не выполняется дважды;
2. одна пачка не захватывает строки другой;
3. сбой внешнего API можно безопасно повторить;
4. состояние можно восстановить после перезапуска;
5. администратор быстро узнает, что фоновые функции перестали работать.

После реализации этих гарантий текущая архитектура с одним Docker-контейнером, SQLite и Google Sheets достаточна для пилота на пять человек.
