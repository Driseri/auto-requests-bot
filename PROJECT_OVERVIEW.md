# Текущее Состояние Проекта

## Назначение Проекта

Проект представляет собой Telegram-бота для сбора заявок на изменение сценариев и ответов чат-ботов.

Система нужна, чтобы сценаристы не передавали правки в свободном формате, а заводили их как структурированные заявки. Бот собирает данные, помогает различить контекст кейса и суть изменения, проверяет через GigaChat практическую полноту описания ADD/EDIT, отправляет заявку в рабочие Google-таблицы направлений и подтверждает автору запись с ID заявки. После этого он уведомляет автора при смене важных статусов, включая `В работе`, или при появлении итогового ответа. Одиночные CHIPS-заявки проходят отдельный сценарий без GigaChat.

Источник правды по заявкам - рабочие таблицы направлений. Единый список заявок является обзорным дашбордом: он помогает смотреть общее состояние, но не предназначен для ручного управления статусами.

## Для Кого Предназначен

**Сценаристы и авторы заявок.** Они создают одиночные заявки или массовые пачки через Telegram-бота, получают ссылки на рабочие строки и уведомления по важным изменениям.

**Редакторы.** Они работают в Google-таблицах направлений: берут заявки в работу, меняют статусы, оставляют комментарии и заполняют итоговый ответ редактора.

**Руководители и координаторы.** Они смотрят общий read-only дашборд, чтобы быстро понять, сколько заявок создано, где они находятся и какие уже закрыты.

**Технические администраторы.** Они поддерживают запуск бота, `.env`, доступы service account, Google-таблицы направлений, GigaChat и Docker/VPS.

## Основная Модель Данных

Система больше не распределяет заявки по листам высокого и низкого приоритета. Заявки распределяются по направлениям:

- `ФЛ`
- `SME`
- `АИ`
- `VoiceBot`
- `Collection`

Для `ФЛ`, `SME`, `АИ` есть тип ответа:

- `Раскатка`
- `Срочные`
- `Интеграция`

Для `VoiceBot` и `Collection` тип ответа не выбирается.

Google-таблицы направлений создаются администратором. Бот не создает новые Google spreadsheet-файлы, но может создавать вкладки внутри уже существующих таблиц.

## Рабочие Таблицы Направлений

Для `ФЛ`, `SME`, `АИ` используется отдельная Google-таблица на каждое направление.

Для `VoiceBot` и `Collection` используется одна общая Google-таблица, но вкладки внутри нее разделяются по направлению.

Заявки типа `Раскатка` распределяются между двумя недельными вкладками. Дата в имени означает понедельник соответствующей недели:

- до среды 14:00 по времени `BOT_TIMEZONE` заявка попадает в первое недельное окно следующей недели, например `08.06 (1)`;
- со среды 14:00 включительно до четверга 14:00 - во второе недельное окно следующей недели, например `08.06 (2)`;
- с четверга 14:00 включительно - в первое недельное окно недели после следующей, например `15.06 (1)`.

Маршрутизация определяется в момент финальной отправки заявки, а не по времени создания черновика. По умолчанию используется московское время; администратор может изменить часовой пояс и дедлайны через `.env`.

Заявки типа `Интеграция` попадают только во вкладку `Интеграции`. Они не дублируются в недельные вкладки.

Вкладки `Срочные` и `Интеграции` дополнительно группируют новые строки по дневным блокам формата `ДД.ММ.ГГ`. При чтении структуры бот использует отображаемые значения Google Sheets, поэтому typed-date строки вроде `02.07.26` распознаются как разделители дня. В `Срочные` CHIPS находится внутри дневного блока рядом с ADD/EDIT. Строка даты не попадает внутрь сворачиваемой группы: группируются только строки заявок под датой, а сама дата остается видимой. Старые строки не мигрируются автоматически; если фоновый daily maintenance не создал блок заранее, первая заявка дня создаёт его при вставке.

## Схема Рабочей Строки

В рабочих вкладках используется единая схема колонок:

1. `Закрепленный сценарист`
2. `Статус`
3. `Кейс или сообщения клиента`
4. `Суть изменений`
5. `Исходный текст`
6. `Итоговый ответ редактора`
7. `Комментарий качества`
8. `Вопросы/комментарии редактора`
9. `Ответ сценариста`
10. `Редактор`
11. `Интент`
12. `ID заявки`
13. `ID пачки`
14. `Тип заявки`
15. `Дата заявки`
16. `Направление`
17. `Тип ответа`
18. `Срочная`
19. `Автор заявки`
20. `Telegram ID`
21. `Исходная суть изменений`
22. `LLM статус`
23. `LLM оценка`
24. `Тип изменения`

Новые рабочие вкладки создаются с колонкой `Статус` в `B`, колонкой `Редактор` в `J` и колонкой `Интент` в `K`. Старые вкладки с прежним порядком колонок и колонкой `Причина изменений` не мигрируются автоматически и продолжают поддерживаться для чтения, записи и polling.

`ID пачки` заполняется только для legacy-массовых пачек. Одиночные заявки и строки новой модели `bulk_reservations` оставляют это поле пустым.

Для заявок типа `Раскатка` поле `Тип изменения` обязательно: `ADD`, `EDIT` или `CHIPS`. В новых недельных вкладках создаются отдельные вертикальные секции для этих типов. Старые недельные вкладки остаются в плоском формате.

`Редактор` назначается только в Google Sheets. По умолчанию новая заявка имеет значение `Редактор не выбран`; доступные редакторы задаются администратором в конфигурации.

## Одиночная Заявка

Одиночная заявка создается через пошаговый сценарий в Telegram.

Сценарий:

1. Выбор направления.
2. Выбор типа ответа, если направление `ФЛ`, `SME` или `АИ`.
3. Интент.
4. Закрепленный сценарист.
5. Кейс или сообщения клиента.
6. Суть изменений.
7. Исходный текст.
8. Признак срочности.
9. Финальная проверка.
10. Отправка.

Перед отправкой пользователь видит итоговую заявку и может отправить ее, отредактировать поля, вернуться назад или отменить.

Если у пользователя задано дефолтное направление, интент или сценарист, бот предлагает быстро подставить эти значения. При необходимости пользователь может выбрать или ввести другое значение.

## Работа GigaChat

GigaChat используется только в одиночных заявках. Он рассматривает сведения из всех переданных полей как один текст и не проверяет наличие отдельных полей заявки.

Заявка проходит проверку, если в тексте прямо указаны содержание изменения и ситуация применения. Для изменения существующего ответа также требуется явная связь текущей проблемы с нужной правкой: например, `сейчас X, нужно Y` или `вместо X указать Y`. Для нового ответа, акции, продукта, услуги, правила или инициативы причина изменения не требуется.

Правило существующего ответа принимает смысловые группы действий добавления, удаления, замены и корректировки, если рядом названо конкретное содержание. Перечисленные в промпте глаголы являются примерами; однозначные синонимы также засчитываются. Текущую проблему можно подтвердить текстом или поведением бота, наблюдаемой проблемой клиента либо уже произошедшим изменением внешних правил и условий.

Стоп-фразы `новый ответ`, `поправить`, `доработать`, `актуализировать`, `по результатам анализа`, `задача от заказчика`, `для удобства` и ссылка без пояснения сами по себе не подтверждают критерии. Они не приводят к отказу, если рядом есть конкретное содержание. Готовая редакционная формулировка и исходный текст на этом шаге не требуются.

По умолчанию используются `prompts/gigachat_system_v3.md` и `prompts/gigachat_user_v3.md`. User-промпт V3 передает только интент, кейс, суть и уточнение, чтобы незаполненные технические поля не влияли на решение. Предыдущие V2 и старые промпты сохранены для отката.

Если описание неполное, бот выбирает один главный блокер и дает одну конкретную инструкцию по дополнению поля. Ответ сценариста добавляется ниже первоначальной сути изменений. После единственного уточнения сценарий идет дальше в любом случае. Если описание все еще неполное, заявка получает пометку `needs_attention`.

Блокер включает номер критерия и правила. Возможные коды: `1.1` для содержания новой сущности, `1.2` для изменения существующего ответа, `2.1` для ситуации применения и `3.1` для причины изменения существующего ответа. Проверка возвращает первый невыполненный код по этому порядку.

Числовая LLM-оценка больше не рассчитывается. Если GigaChat недоступен или вернул некорректный ответ, заявка не блокируется. Бот сохраняет пользовательское описание и продолжает сценарий со статусом `error`.

## Массовые Заявки

Актуальная модель новых массовых заявок работает через `bulk_reservations`: бот резервирует выбранное пользователем количество строк прямо в целевом рабочем листе (`Срочные`, недельная вкладка или `Интеграции`), а после подтверждения регистрирует заполненные строки как обычные одиночные заявки. Новые массовые строки не получают `ID пачки`; старый workflow `bulk_batches` ниже оставлен как legacy-совместимость для уже отправленных старых сообщений.

Массовая заявка нужна для случаев, когда сценаристу нужно передать много строк сразу.

Сценарий массовой заявки:

1. Пользователь выбирает `Массовая заявка`.
2. Выбирает направление.
3. Выбирает место: `Срочные`, недельная вкладка или `Интеграции`.
4. Выбирает тип изменения: `ADD`, `EDIT` или `CHIPS`.
5. Вводит количество строк, не больше `BULK_MAX_ROWS`.
6. Бот вставляет это количество пустых строк в конец нужной секции и подсвечивает обязательные колонки.
7. Пользователь вручную заполняет строки в Google Sheets.
8. Пользователь нажимает `Заявка заполнена`; бот валидирует строки, присваивает каждой заполненной строке `ID заявки`, ставит статус `Новая` и сохраняет tracking/dashboard как для одиночных заявок.

Новая массовая модель не создает `ID пачки` и не требует отдельного staging-листа. `bulk_reservations` хранит только резерв, координаты и состояние регистрации. Пустые строки остаются пустыми, частично заполненные строки блокируют регистрацию до исправления.

Создание и регистрация защищены section-lock, idempotency key и Google `developerMetadata`. Перед регистрацией бот ищет актуальный диапазон резерва по metadata, поэтому ручная вставка или удаление строк выше резерва не должны ломать координаты. GigaChat в массовом режиме не используется.

Legacy workflow `bulk_batches` оставлен только для уже отправленных старых сообщений и старых данных.

## Дашборд

Дашборд - отдельная Google-таблица для общего просмотра состояния заявок.

Он содержит компактную информацию:

1. `ID заявки`
2. `ID пачки`
3. `Дата заявки`
4. `Направление`
5. `Тип заявки`
6. `Тип ответа`
7. `Срочная`
8. `Автор заявки`
9. `Статус`
10. `Редактор`
11. `Итоговый ответ есть`
12. `Ссылка на рабочую строку`

Бот автоматически создает или обновляет строки дашборда по `ID заявки`. Для legacy `bulk_batches` сохранена поддержка старой проекции по `ID пачки`, но новая массовая модель пишет в дашборд только отдельные application-строки. Последняя требуемая проекция хранится в SQLite `dashboard_outbox` до успешной пакетной записи, поэтому внешний сбой дашборда не влияет на основной workflow. Если пользователь вручную изменит дашборд, эти изменения не считаются источником правды и могут быть перезаписаны следующей синхронизацией.

## Статусы И Уведомления

Одиночные заявки используют статусы:

- `Новая`
- `В работе`
- `Нужны пояснения`
- `Итоговый ответ готов`
- `Принята`
- `Отклонена`
- `Отложена`
- `Удаление`

Автор получает уведомление, когда одиночная заявка переходит в один из важных статусов:

- `В работе`;

- `Итоговый ответ готов`
- `Принята`
- `Отклонена`
- `Отложена`

Строки внутри новых массовых заявок используют три статуса: `Новая`, `Нужны пояснения`, `Принято`. Статусы всей новой массовой заявки: `Новая пачка`, `В работе`, `Готова`. Старые массовые заявки сохраняют существующие dropdown без автоматического изменения.

Статус `Удаление` не отправляет обычные уведомления. Polling считает его подтвержденным только после двух одинаковых наблюдений подряд, затем бот перечитывает строку, проверяет `ID заявки` и удаляет строку из Google Sheets, tracking, outbox и dashboard projection. Если статус изменился до второго наблюдения, pending-удаление сбрасывается. Несколько удалений в одном листе выполняются снизу вверх, чтобы физический сдвиг строк после `deleteDimension` не приводил к проверке устаревших координат.

Новые массовые пачки создаются с колонкой `Кейс или сообщения клиента`; ранее созданные пачки с колонкой `Причина изменений` продолжают распознаваться.

Для одиночной заявки итоговый ответ отправляется автору после перехода в статус `Итоговый ответ готов`. Комментарий редактора отправляется автору не по статусу, а после того как поле `Вопросы/комментарии редактора` остаётся одинаковым 3 polling-цикла подряд. Для срочных одиночных заявок ответ сценариста из поля `Ответ сценариста` отправляется в чат редакторов после такой же стабилизации.

По массовой заявке Telegram-уведомление отправляется при переходе всей пачки в статус `Готова`. Также автор получает одно сгруппированное уведомление, когда внутри пачки появляются новые строки со статусом `Нужны пояснения`; сообщение содержит ссылки на эти строки и комментарии редактора. Повторные уведомления по неизменившимся строкам, статус `Принято` и итоговые ответы строк не отправляются.

Все ссылки в уведомлениях ведут на актуальную рабочую строку в Google Sheets. Система ищет заявки по `ID заявки`, поэтому сортировка и перемещение строк в таблице не ломают ссылки. Обнаруженные polling-события сначала атомарно сохраняются в SQLite outbox вместе с tracking-состоянием. Telegram-доставка и дашборд обрабатываются независимо; временная ошибка одного этапа не откатывает остальные.

Служебные зоны рабочих листов защищаются best-effort: технические колонки, основные шапки, строки дат и CHIPS-маркеры получают protected ranges. Колонка `A` не защищается целиком, чтобы не блокировать заполнение `Закрепленного сценариста` в массовых резервах. Ошибка создания защиты логируется, но не блокирует запись заявки.

Polling одиночных заявок работает через fast path: для tracking-записей с координатами бот читает конкретные строки через Google `values.batchGet`. Если координаты устарели, строка пуста, `ID заявки` не совпал или координат нет, используется текущий fallback scan листа и координаты восстанавливаются по `ID заявки`.

## Срочные Ответы

В заявках есть поле `Срочная` со значением `Да` или `Нет`. В рабочих таблицах срочность не подсвечивается отдельной бежевой заливкой; дашборд и маршрутизация остаются источником визуального контекста по срочности.

Бизнес-правила для срочных ответов пока не зафиксированы. На текущем этапе это только признак и визуальная подсветка.

## Форматирование Исходного Текста

В одиночных заявках бот сохраняет жирное и зачеркнутое форматирование, если пользователь отправил его в Telegram на этапе `Исходный текст`.

Это форматирование переносится в Google Sheets в колонку `Исходный текст` как rich text.

Другие виды Telegram-форматирования не поддерживаются. В массовом режиме rich text не переносится, потому что строки вставляются пользователем вручную в Google Sheets.

## Актуальные Уточнения По Срочности, Дашборду И Массовым Заявкам

Срочность в одиночной заявке выбирается один раз. Для `ФЛ`, `SME`, `АИ` срочность определяется типом ответа: `Срочные` делает заявку срочной, `Раскатка` и `Интеграция` - обычной. Для `VoiceBot` и `Collection` бот отдельно спрашивает, является ли заявка обычной или срочной.

Срочные заявки живут в отдельных вкладках `Срочные` внутри таблиц направлений. Они не дублируются в недельных вкладках. Заявки типа `Интеграция` записываются только во вкладку `Интеграции`, даже если у старых данных одновременно указан признак срочности.

Дашборд содержит один лист `Заявки`. В нем каждая зарегистрированная строка отображается отдельной заявкой. Новая массовая модель `bulk_reservations` не создает агрегированную строку пачки; строки резерва после регистрации попадают в дашборд как обычные одиночные заявки с пустым `ID пачки`. Legacy `bulk_batches` продолжает поддерживаться для старых данных.

Колонка `Итоговый ответ есть` показывает `Да`, если редактор уже заполнил итоговый ответ в рабочей строке ADD/EDIT. Для CHIPS значение всегда `Нет`.

Синхронизация читает `Заявки!A:L` один раз за проход и применяет накопленные проекции одним пакетным запросом. При обнаружении дублей первая строка остается канонической, данные объединяются без потерь, а лишние строки удаляются снизу вверх.

Массовая вставка работает через резерв строк в выбранной рабочей секции. При создании резерва бот подсвечивает обязательные пользовательские колонки; толстые границы ставятся только после успешной регистрации заполненных строк. Пустые строки после регистрации не считаются очередью бота и не регистрируются автоматически позже.

## Хранение Данных

Черновики, пользовательские дефолты, отправленные заявки, bulk reservations, notification outbox и dashboard outbox хранятся в SQLite.

Один пользователь имеет один активный черновик. Черновики и настройки переживают перезапуск контейнера, потому что SQLite хранится в Docker volume.

После успешной отправки одиночная заявка помечается завершенной. Отправленные заявки остаются в tracking-таблице SQLite, чтобы бот мог отслеживать их статусы и итоговые ответы.

## Запуск И Окружение

Проект запускается в Docker. На VPS бот работает через polling, поэтому ему не нужен домен, публичный HTTP endpoint или webhook.

Контейнер использует временную зону `Europe/Moscow` по умолчанию. Бизнес-расчет расписания выполняется самим приложением по настройкам `BOT_TIMEZONE`, `ROLLOUT_WEDNESDAY_CUTOFF` и `ROLLOUT_THURSDAY_CUTOFF`, поэтому не зависит от системной зоны VPS.

Для работы нужны:

- Telegram bot token;
- Google service account credentials;
- ID дашборда;
- ID таблиц направлений;
- GigaChat credentials;
- SQLite volume;
- proxy для Telegram API, если прямой доступ с VPS недоступен.

Секреты хранятся в `.env` и `credentials.json`. Их нельзя публиковать в репозитории.

## Текущие Ограничения

- Админ-панели нет.
- Ролевой модели внутри Telegram-бота нет.
- Справочник интентов и сценаристов не реализован.
- Ответ сценариста через Telegram пока не пишется обратно в таблицу.
- Массовый режим работает через ручную вставку строк в Google Sheets, а не через загрузку файла в бот.
- Новая массовая заявка работает через резерв строк в целевой секции; старый лист `Массовый ввод` используется только legacy-сценариями.
- Автоматическая миграция старых таблиц `Высокий`, `Низкий`, `Массовые` в новую модель не выполняется.
- Старые рабочие схемы не перестраиваются автоматически; бот продолжает читать и заполнять их в прежнем порядке.
- Для срочных заявок `ФЛ`, `SME`, `АИ` обязателен тип изменения; внутри каждого дневного блока ADD/EDIT находятся в общей части, а CHIPS — в локальной секции этого дня.
- Для раскатки используются подтвержденные типы `ADD`, `EDIT`, `CHIPS`.
- Временные ошибки Google API (`429`, `5xx`, timeout, broken pipe, reset соединения)
  повторяются с ограниченным exponential backoff и jitter. Постоянные ошибки прав и схемы
  не повторяются.
## Как Понять, Что Система Работает

Система работает корректно, если:

- бот отвечает в Telegram;
- в логах есть `Start polling`;
- пользователь может создать одиночную заявку;
- заявка появляется в правильной таблице направления и правильной вкладке;
- интеграционная заявка попадает во вкладку `Интеграции`;
- массовая заявка создает место вставки, а кнопка `Заявка заполнена` регистрирует заполненные строки;
- дашборд получает или обновляет строки по заявкам;
- при изменении важного статуса автор получает уведомление;
- при заполнении итогового ответа редактора автор получает текст ответа в Telegram.
## Отдельная схема CHIPS

Одиночные заявки `CHIPS`, включая срочные, не проходят проверку GigaChat. Бот собирает закреплённого сценариста, интент, причину, текст до чипса и текст чипса, затем уточняет действие с ответом после чипса: `ADD`, `EDIT` или без изменений. Для `ADD`/`EDIT` пользователь также заполняет суть изменения текста ответа; бот добавляет служебную фразу со связью с ID CHIPS в конец этого описания. После этого пользователь вводит текст после чипса и видит в review, будет создана одна или две заявки. В SQLite LLM-проверка отмечается как `skipped`.

Для `ADD`/`EDIT` бот одной Google `batchUpdate`-операцией создаёт CHIPS-строку и отдельную строку соответствующего типа. Второй ID детерминирован от ID CHIPS, что делает retry идемпотентным. Ячейки с текстом после чипса и с текстом ADD/EDIT получают взаимные Google Sheets notes с ID и ссылкой на строку второй заявки. Два section-lock удерживаются до общей SQLite-транзакции, которая сохраняет две обычные tracking-записи и две dashboard-проекции. Отдельной связи в SQLite нет: после отправки статусы, уведомления и удаление работают для строк независимо. Если при retry найдена только одна строка или вычисленный ID занят посторонней заявкой, операция завершается fail-closed без автоматической дозаписи.

Новые CHIPS-секции недельных листов используют отдельную схему `A:U`. `Статус` находится в `B`, `Редактор` - в `J`, `Интент` - в `K`, ID заявки находится в `L`, а тип изменения в `U`. Три текстовых фрагмента записываются в `D:F` с сохранением Telegram rich text.

Пустая legacy-секция CHIPS обновляется на месте. Если legacy-секция содержит данные, она остаётся неизменной, а новые записи направляются в добавленную секцию `CHIPS V2`. Polling распознаёт обе схемы. Для CHIPS отслеживаются важные статусы и комментарий редактора; признак итогового ответа в общем дашборде всегда равен `Нет`.

Лист `Срочные` имеет дневной hybrid-layout: внутри каждого блока `ДД.ММ.ГГ` сначала идут ADD/EDIT, затем локальный маркер `CHIPS`, шапка `A:U` и CHIPS-строки этого дня. Парная CHIPS + ADD/EDIT вставка помещает обе строки в соответствующие части одного дневного блока.

Массовый workflow не изменён.
