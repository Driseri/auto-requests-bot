# Alfa Auto Requests Bot

Telegram-бот для сбора заявок на изменение сценариев и ответов чат-ботов. Бот помогает сценаристам быстро заводить одиночные заявки и массовые заявки, отправляет данные в рабочие Google-таблицы направлений, синхронизирует read-only дашборд и уведомляет автора о важных изменениях статуса и итоговых ответах редактора.

## Что Реализовано

- Telegram-бот на `aiogram 3` с polling.
- Одиночные заявки с выбором направления, типа ответа и финальной проверкой перед отправкой; GigaChat проверяет ADD/EDIT, а CHIPS проходит отдельный сценарий без LLM.
- Массовые заявки: бот создает место в таблице направления, пользователь вставляет строки вручную и подтверждает заполнение кнопкой в Telegram.
- Google Sheets routing по направлениям: `ФЛ`, `SME`, `АИ`, `VoiceBot`, `Collection`.
- Для заявок `Раскатка` обязателен тип изменения `ADD`, `EDIT` или `CHIPS`. Недельные вкладки разделены на окна среды и четверга, а новые вкладки содержат отдельные вертикальные секции для каждого типа.
- Отдельная вкладка `Интеграции` для интеграционных заявок.
- Read-only дашборд с компактным списком заявок и ссылками на рабочие строки.
- Уведомления по важным статусам и появлению итогового ответа редактора.
- SQLite-хранение черновиков, дефолтов пользователя, отправленных заявок и массовых заявок.
- Пользовательские дефолты для направления, интента и сценариста.
- ID заявки длиной 8 символов.
- Rich text перенос жирного и зачеркнутого Telegram-форматирования для поля `Исходный текст`, а для CHIPS отдельно для трёх текстовых фрагментов.

## Актуальная Логика Срочности, Дашборда И Массовой Вставки

Срочность выбирается один раз. Для направлений `ФЛ`, `SME`, `АИ` она определяется типом ответа: `Срочные` означает `Срочная = Да`, `Раскатка` и `Интеграция` означают `Срочная = Нет`. Для `VoiceBot` и `Collection` тип ответа не выбирается, поэтому бот отдельно спрашивает `Обычная` / `Срочная`.

Срочные заявки не дублируются в недельные вкладки. Они записываются только во вкладку `Срочные`; для общей таблицы `VoiceBot` / `Collection` используются вкладки `VoiceBot Срочные` и `Collection Срочные`. Для срочных заявок `ФЛ`, `SME`, `АИ` обязателен тип изменения `ADD`, `EDIT` или `CHIPS`. ADD/EDIT остаются в общей верхней таблице, а CHIPS записывается в отдельную секцию внизу листа. Заявки типа `Интеграция` имеют приоритет маршрутизации и записываются только во вкладку `Интеграции`.

Дашборд использует один лист `Заявки`: каждая зарегистрированная строка отображается отдельной заявкой. Новая массовая модель `bulk_reservations` не создает агрегированную строку пачки и не заполняет `ID пачки`; строки массового резерва после регистрации попадают в дашборд как обычные одиночные заявки. Колонка `Итоговый ответ есть` содержит только `Да` или `Нет`: для CHIPS всегда `Нет`, для ADD/EDIT — наличие текста в поле `Итоговый ответ редактора`.

Массовая вставка работает через резерв строк в выбранном рабочем месте: `Срочные`, недельная вкладка или `Интеграции`. Пользователь выбирает направление, место, тип изменения и количество строк; бот вставляет пустой диапазон в конец нужной секции, подсвечивает обязательные пользовательские колонки, а после кнопки `Заявка заполнена` регистрирует заполненные строки как обычные заявки. Старый workflow `bulk_batches` и лист `Массовый ввод` сохранены только для legacy-совместимости со старыми сообщениями.

## Конфигурация

Создайте `.env` по примеру `.env.example`. Для пилота на 5 пользователей рекомендуется
сначала использовать значения ниже и менять их только при наличии конкретной причины:

```env
TELEGRAM_BOT_TOKEN=123456:telegram-token
TELEGRAM_PROXY_URL=
TELEGRAM_REQUEST_TIMEOUT=60
SQLITE_PATH=/data/app.db

BOT_TIMEZONE=Europe/Moscow
ROLLOUT_WEDNESDAY_CUTOFF=14:00
ROLLOUT_THURSDAY_CUTOFF=14:00
APPLICATION_EDITORS=редактор 1,редактор 2

GOOGLE_CREDENTIALS_PATH=/run/secrets/google_credentials.json
GOOGLE_FL_SPREADSHEET_ID=fl-spreadsheet-id
GOOGLE_SME_SPREADSHEET_ID=sme-spreadsheet-id
GOOGLE_AI_SPREADSHEET_ID=ai-spreadsheet-id
GOOGLE_VOICE_COLLECTION_SPREADSHEET_ID=voice-collection-spreadsheet-id
GOOGLE_DASHBOARD_SPREADSHEET_ID=dashboard-spreadsheet-id

GIGACHAT_CREDENTIALS=gigachat-authorization-key
GIGACHAT_BASE_URL=https://gigachat.devices.sberbank.ru/api/v1
GIGACHAT_AUTH_URL=https://ngw.devices.sberbank.ru:9443/api/v2/oauth
GIGACHAT_SCOPE=GIGACHAT_API_PERS
GIGACHAT_MODEL=GigaChat
GIGACHAT_VERIFY_SSL_CERTS=true
GIGACHAT_CA_BUNDLE_FILE=
GIGACHAT_TIMEOUT=60
GIGACHAT_MAX_RETRIES=3
GIGACHAT_RETRY_BACKOFF_FACTOR=1
GIGACHAT_SYSTEM_PROMPT_PATH=prompts/gigachat_system_v2.md
GIGACHAT_USER_PROMPT_PATH=prompts/gigachat_user_v2.md
GIGACHAT_SHOW_RESPONSE_JSON=false

STATUS_POLLING_ENABLED=true
STATUS_POLLING_INTERVAL_SECONDS=30
STATUS_POLLING_MEMORY_LOG_INTERVAL=40
STATUS_POLLING_HEARTBEAT_PATH=/data/status-polling-heartbeat.json
STATUS_NOT_FOUND_THRESHOLD=20
STATUS_NOT_FOUND_RECHECK_SECONDS=3600
STATUS_POLLING_HEARTBEAT_MAX_AGE_SECONDS=180

HEALTH_EXTERNAL_CHECK_INTERVAL_SECONDS=300
HEALTH_EXTERNAL_FAILURE_THRESHOLD=2
HEALTH_EXTERNAL_TIMEOUT_SECONDS=10
HEALTH_EXTERNAL_CACHE_PATH=/data/external-health.json

DASHBOARD_SYNC_INTERVAL_SECONDS=300
COMPLETED_BULK_DASHBOARD_SCAN_INTERVAL_SECONDS=3600
BULK_RELOCATION_SEARCH_INTERVAL_SECONDS=3600
DASHBOARD_OUTBOX_RETRY_BASE_SECONDS=60
DASHBOARD_OUTBOX_RETRY_MAX_SECONDS=3600
DASHBOARD_OUTBOX_SENDING_STALE_SECONDS=300

BULK_RESERVED_ROWS=100
BULK_REGISTRATION_STALE_SECONDS=600
BULK_CREATION_STALE_SECONDS=600

NOTIFICATION_MAX_ATTEMPTS=10
NOTIFICATION_RETRY_BASE_SECONDS=30
NOTIFICATION_SENDING_STALE_SECONDS=300
NOTIFICATION_MESSAGE_MAX_CHARS=3500
URGENT_EDITOR_NOTIFICATIONS_ENABLED=false
EDITOR_URGENT_CHAT_ID=

GOOGLE_API_MAX_ATTEMPTS=4
GOOGLE_API_RETRY_BASE_SECONDS=1
GOOGLE_API_RETRY_MAX_SECONDS=8

BACKUP_DIR=./backups
```

Значения `true` и `false` следует указывать без кавычек. После изменения `.env`
пересоздайте контейнер командой:

```bash
docker compose up -d --force-recreate bot
```

Пересборка образа для изменения только конфигурации не требуется.

`MALLOC_ARENA_MAX=2` задается в Compose для основного контейнера `bot`.
Это ограничивает рост аллокатора памяти при фоновых Google API запросах и не
требует отдельной настройки в `.env`.
После polling-циклов бот дополнительно выполняет `gc.collect()` и, если доступно
в Linux, `malloc_trim(0)`, чтобы снизить удержание heap после тяжелых Google
Sheets операций.

### Обязательные Переменные

| Переменная | Как выставлять |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен рабочего Telegram-бота. Без него приложение не запускается. |
| `GOOGLE_CREDENTIALS_PATH` | В Docker оставлять `/run/secrets/google_credentials.json`. Файл хоста `./credentials.json` монтируется туда через Compose. |
| `GOOGLE_FL_SPREADSHEET_ID` | ID рабочей таблицы направления `ФЛ`. |
| `GOOGLE_SME_SPREADSHEET_ID` | ID рабочей таблицы направления `SME`. |
| `GOOGLE_AI_SPREADSHEET_ID` | ID рабочей таблицы направления `АИ`. |
| `GOOGLE_VOICE_COLLECTION_SPREADSHEET_ID` | ID общей рабочей таблицы `VoiceBot` и `Collection`. |
| `GIGACHAT_CREDENTIALS` | Авторизационные данные GigaChat для проверки полноты заявки. |

Все четыре рабочие Google-таблицы считаются обязательными. Даже если во время пилота
одно направление временно не используется, пустой ID приведет к состоянию `unhealthy`.
Service account должен иметь права редактора во всех рабочих таблицах.

`GOOGLE_DASHBOARD_SPREADSHEET_ID` формально необязателен. Если оставить его пустым,
основные заявки и уведомления продолжат работать, но общий дашборд не будет
синхронизироваться и healthcheck не станет проверять доступ к нему.

Google-таблицы создаются администратором вручную. Бот не создает spreadsheet-файлы,
но создает и форматирует необходимые вкладки внутри указанных таблиц.

### Telegram И Локальные Данные

| Переменная | Рекомендация и логика |
|---|---|
| `TELEGRAM_PROXY_URL` | Оставлять пустой, если сервер напрямую обращается к Telegram. Заполнять полным URL прокси только при сетевой необходимости. Этот же прокси используется healthcheck. |
| `TELEGRAM_REQUEST_TIMEOUT` | `60` секунд. Уменьшать можно только при стабильной сети; слишком малое значение создаст ложные ошибки отправки. |
| `SQLITE_PATH` | В Docker оставлять `/data/app.db`, потому что `/data` находится в постоянном volume. Не указывать путь внутри непостоянной файловой системы контейнера. |
| `BOT_TIMEZONE` | IANA timezone, например `Europe/Moscow`. Она применяется к маршрутизации раскаток и новым датам Google Sheets. Изменение влияет только на новые записи. |
| `APPLICATION_EDITORS` | Имена через запятую без пустых элементов. Они становятся значениями dropdown в новых строках и вкладках. |

`ROLLOUT_WEDNESDAY_CUTOFF` и `ROLLOUT_THURSDAY_CUTOFF` задаются в формате `HH:MM`
по `BOT_TIMEZONE`. Обычно их следует менять вместе с бизнес-регламентом. Дедлайн
четверга должен идти после дедлайна среды в рамках недельной логики.

### Google Sheets И Retry

| Переменная | Рекомендация и логика |
|---|---|
| `GOOGLE_API_MAX_ATTEMPTS` | `4`: первоначальная попытка и до трех повторов временных ошибок. Постоянные `403`, ошибки прав и схемы не повторяются. |
| `GOOGLE_API_RETRY_BASE_SECONDS` | `1`: начальная задержка exponential backoff. |
| `GOOGLE_API_RETRY_MAX_SECONDS` | `8`: верхняя граница задержки одной операции. Должна быть не меньше `GOOGLE_API_RETRY_BASE_SECONDS`. |

Увеличивать число попыток стоит только при нестабильной сети. Это повышает шанс
успешного завершения, но также увеличивает время ответа пользователю. Для пилота
`4 / 1 / 8` является сбалансированным профилем.

### GigaChat

| Переменная | Рекомендация и логика |
|---|---|
| `GIGACHAT_BASE_URL`, `GIGACHAT_AUTH_URL` | Оставлять стандартными, если провайдер не выдал другие адреса. |
| `GIGACHAT_SCOPE` | Должен соответствовать выданным credentials. Для текущего пилота используется `GIGACHAT_API_PERS`. |
| `GIGACHAT_MODEL` | Оставлять `GigaChat`, пока смена модели не проверена на текущем JSON-контракте. |
| `GIGACHAT_VERIFY_SSL_CERTS` | В production оставлять `true`. |
| `GIGACHAT_CA_BUNDLE_FILE` | Оставлять пустым при стандартном доверенном сертификате. Указывать путь только для корпоративного CA bundle. |
| `GIGACHAT_TIMEOUT` | `60` секунд. Это предельное время одного запроса проверки. |
| `GIGACHAT_MAX_RETRIES` | `3` для временных сетевых ошибок. |
| `GIGACHAT_RETRY_BACKOFF_FACTOR` | `1`; увеличение замедляет повторы. |
| `GIGACHAT_SYSTEM_PROMPT_PATH`, `GIGACHAT_USER_PROMPT_PATH` | По умолчанию используются `prompts/gigachat_system_v2.md` и `prompts/gigachat_user_v2.md`. Для полного отката укажите старые `prompts/gigachat_system.md` и `prompts/gigachat_user.md`. |
| `GIGACHAT_SHOW_RESPONSE_JSON` | `false` в обычной работе. `true` использовать только для диагностики структуры ответа. |

### Polling И Heartbeat

| Переменная | Рекомендация и логика |
|---|---|
| `STATUS_POLLING_ENABLED` | Для production оставлять `true`. При `false` бот не отслеживает изменения статусов, не отправляет фоновые уведомления и не обновляет дашборд по изменениям таблиц. |
| `STATUS_POLLING_INTERVAL_SECONDS` | `30` для пилота. Меньшее значение быстрее обнаруживает изменения, но чаще обращается к Google API. |
| `STATUS_POLLING_MEMORY_LOG_INTERVAL` | `40`: как часто писать RSS/VMS память polling-цикла в лог. При polling 30 секунд это примерно раз в 20 минут. `0` отключает этот лог. |
| `STATUS_POLLING_HEARTBEAT_PATH` | В Docker оставлять `/data/status-polling-heartbeat.json`. |
| `STATUS_NOT_FOUND_THRESHOLD` | `20`: сколько последовательных polling-циклов заявка может не находиться в Google Sheets, прежде чем она уйдет в редкую перепроверку. |
| `STATUS_NOT_FOUND_RECHECK_SECONDS` | `3600`: как часто повторно проверять долго не найденные заявки. Это снижает нагрузку и шум в логах, но сохраняет восстановление, если строка появится снова. |
| `STATUS_POLLING_HEARTBEAT_MAX_AGE_SECONDS` | Рекомендуется не меньше `max(180, STATUS_POLLING_INTERVAL_SECONDS * 3)`. |

Heartbeat обновляется только после полностью успешного polling-цикла. Поэтому слишком
малый `STATUS_POLLING_HEARTBEAT_MAX_AGE_SECONDS` будет переводить контейнер в
`unhealthy` при одном медленном цикле Google API.

Для 5 пользователей рекомендуется интервал `30` секунд. Значения меньше `15` секунд
обычно не дают заметного выигрыша для пользователя, но увеличивают расход квоты.

### Healthcheck

| Переменная | Рекомендация и логика |
|---|---|
| `HEALTH_EXTERNAL_CHECK_INTERVAL_SECONDS` | `300`: реальные `Telegram getMe` и Google probes выполняются не чаще раза в 5 минут. |
| `HEALTH_EXTERNAL_FAILURE_THRESHOLD` | `2`: после ранее успешной проверки один внешний сбой допускается, второй подряд дает `unhealthy`. До первого успеха критичен первый сбой. |
| `HEALTH_EXTERNAL_TIMEOUT_SECONDS` | `10`: timeout каждой внешней проверки. |
| `HEALTH_EXTERNAL_CACHE_PATH` | В Docker оставлять `/data/external-health.json`, чтобы атомарный кэш переживал restart контейнера. |

Не следует ставить внешний интервал равным Docker healthcheck interval `30s`: это
создаст лишние запросы к Telegram и Google. Значение `300` оставляет локальные проверки
частыми, а внешние проверки делает экономными.

### Дашборд И Dashboard Outbox

| Переменная | Рекомендация и логика |
|---|---|
| `DASHBOARD_SYNC_INTERVAL_SECONDS` | `300`: периодическая постановка актуальных проекций одиночных и активных массовых заявок. Изменения статуса также ставятся в outbox сразу при обнаружении. |
| `COMPLETED_BULK_DASHBOARD_SCAN_INTERVAL_SECONDS` | `3600`: завершенные пачки проверяются раз в час для поздних итоговых ответов и смены редактора. |
| `BULK_RELOCATION_SEARCH_INTERVAL_SECONDS` | `3600`: повторный полный поиск перемещенной массовой пачки на ее исходном физическом листе. Первая попытка выполняется сразу после потери сохраненных координат. |
| `DASHBOARD_OUTBOX_RETRY_BASE_SECONDS` | `60`: задержка после первой неудачной пакетной записи. |
| `DASHBOARD_OUTBOX_RETRY_MAX_SECONDS` | `3600`: максимальная задержка между повторами. Проекции повторяются бессрочно. |
| `DASHBOARD_OUTBOX_SENDING_STALE_SECONDS` | `300`: зависшая запись `SENDING` возвращается в `PENDING` через 5 минут. |

`DASHBOARD_OUTBOX_SENDING_STALE_SECONDS` должен быть больше ожидаемой длительности
одного пакетного Google-запроса со всеми внутренними retry. Уменьшение этого значения
может привести к повторному захвату еще выполняющейся операции.

### Массовые Заявки

| Переменная | Рекомендация и логика |
|---|---|
| `BULK_MAX_ROWS` | `50`: максимальное количество строк, которое пользователь может зарезервировать в новом массовом workflow `bulk_reservations`. |
| `BULK_RESERVED_ROWS` | `100`: legacy-резерв строк для старого workflow `bulk_batches`. Новый UI его не использует, но старые callback-сообщения остаются поддерживаемыми. |
| `BULK_REGISTRATION_STALE_SECONDS` | `600`: через сколько зависшая регистрация может быть безопасно повторена. |
| `BULK_CREATION_STALE_SECONDS` | `600`: через сколько зависшее создание пачки может быть восстановлено. |
| `DAILY_SHEET_GROUPING_ENABLED` | `true`: новые строки в `Срочные` и `Интеграции` попадают в дневные блоки `ДД.ММ.ГГ`. |
| `DAILY_SHEET_MAINTENANCE_ENABLED` | `true`: фоновый проход заранее создаёт дневные блоки в существующих срочных/интеграционных листах. |
| `DAILY_SHEET_MAINTENANCE_TIME` | `00:01`: локальное время `BOT_TIMEZONE` для вспомогательного daily maintenance. |

Stale-интервалы должны быть больше максимального нормального времени соответствующей
Google-операции. Для пилота не рекомендуется ставить их ниже `300` секунд. Увеличение
`BULK_MAX_ROWS` ограничивает размер нового массового резерва, чтобы не создавать слишком
большие пустые блоки в рабочих листах. `BULK_RESERVED_ROWS` оставлен для старых пачек.

### Уведомления

| Переменная | Рекомендация и логика |
|---|---|
| `NOTIFICATION_MAX_ATTEMPTS` | `10`: после десятой ошибки часть сообщения переходит в `FAILED`. |
| `NOTIFICATION_RETRY_BASE_SECONDS` | `30`: база ограниченного exponential backoff. |
| `NOTIFICATION_SENDING_STALE_SECONDS` | `300`: возврат зависшей доставки из `SENDING` в `PENDING`. |
| `NOTIFICATION_MESSAGE_MAX_CHARS` | `3500`: безопасный лимит ниже ограничения Telegram `4096`, учитывающий HTML-разметку. |
| `URGENT_EDITOR_NOTIFICATIONS_ENABLED` | `false` по умолчанию. При `true` бот ставит durable-уведомление в общий чат редакторов после успешного создания одиночной срочной заявки. |
| `EDITOR_URGENT_CHAT_ID` | Telegram chat id общего чата редакторов. Для supergroup обычно начинается с `-100`. Обязателен, если `URGENT_EDITOR_NOTIFICATIONS_ENABLED=true`. |

Не рекомендуется повышать `NOTIFICATION_MESSAGE_MAX_CHARS` выше `3500`. Уменьшение
допустимо, но создаст больше отдельных Telegram-сообщений. Stale timeout должен быть
больше `TELEGRAM_REQUEST_TIMEOUT`.

Для уведомлений редакторов добавьте бота в общий чат редакторов, получите `chat_id`,
заполните `EDITOR_URGENT_CHAT_ID`, включите
`URGENT_EDITOR_NOTIFICATIONS_ENABLED=true` и пересоздайте контейнер. Healthcheck не
отправляет тестовые сообщения в чат, чтобы не спамить редакторов; проверка выполняется
через создание тестовой срочной заявки.

Чтобы получить `chat_id`, добавьте бота в группу и напишите любое сообщение в этот
чат. Бот не будет отвечать в группе, но запишет в логи строку
`Ignored non-private chat update: chat_id=...`. Посмотреть ее можно командой:

```bash
docker compose -f docker-compose.prod.yml logs --since=10m bot \
  | grep 'Ignored non-private chat update'
```

### Production Image И Backup

`APP_VERSION` нужен только для `docker-compose.prod.yml` и задает неизменяемый тег
образа, например commit SHA:

```env
APP_VERSION=4f2c9ab
BACKUP_DIR=./backups
```

Перед production-запуском образ с таким тегом уже должен существовать локально или в
registry. Один и тот же `APP_VERSION` используется контейнерами `bot` и `backup`.

`BACKUP_DIR` — каталог хоста, в который maintenance-контейнер записывает резервные
копии. Относительный путь считается от каталога Compose-проекта. Для VPS можно
использовать абсолютный путь, например `/opt/alfa-auto-requests/backups`.

### Правила Изменения Конфигурации

1. Сначала меняйте только одну группу параметров и фиксируйте причину изменения.
2. После изменения интервала polling пересчитайте допустимый возраст heartbeat.
3. После изменения сетевых timeout проверьте, что соответствующие stale timeout больше них.
4. После изменения `BOT_TIMEZONE` или дедлайнов проверьте маршрутизацию новой тестовой заявки.
5. После изменения списка редакторов создайте новую строку и проверьте dropdown; существующие validation rules автоматически не мигрируют.
6. После изменения Google ID или credentials выполните `docker compose exec bot python -m app.health`.
7. Не удаляйте Docker volume при обычном обновлении конфигурации: в нем находятся SQLite, heartbeat и health-кэш.

Старые переменные `GOOGLE_SPREADSHEET_ID`, `GOOGLE_HIGH_PRIORITY_SHEET_NAME`,
`GOOGLE_LOW_PRIORITY_SHEET_NAME`, `GOOGLE_BULK_SHEET_NAME` оставлены только для
временной совместимости старых `.env`. Новая маршрутизация их не использует, поэтому
для новой установки их следует оставить пустыми.

## Направления И Вкладки

Пользователь выбирает направление:

- `ФЛ`
- `SME`
- `АИ`
- `VoiceBot`
- `Collection`

Для `ФЛ`, `SME`, `АИ` дополнительно выбирается тип ответа:

- `Раскатка`
- `Срочные`
- `Интеграция`

Для `VoiceBot` и `Collection` тип ответа не выбирается.

Заявки типа `Раскатка` распределяются по времени фактической отправки:

- до среды 14:00 по времени `BOT_TIMEZONE` - в первое недельное окно следующей недели, например `08.06 (1)`;
- со среды 14:00 включительно до четверга 14:00 - во второе недельное окно следующей недели, например `08.06 (2)`;
- с четверга 14:00 включительно - в первое недельное окно недели после следующей, например `15.06 (1)`.

Дата в имени - понедельник соответствующей недели. Часовой пояс и оба дедлайна настраиваются через `BOT_TIMEZONE`, `ROLLOUT_WEDNESDAY_CUTOFF` и `ROLLOUT_THURSDAY_CUTOFF`. Дата создания черновика на маршрутизацию не влияет.

Заявки типа `Интеграция` попадают только во вкладку `Интеграции` и не дублируются в недельную вкладку. Срочные заявки попадают только в `Срочные`. Для общей таблицы `VoiceBot`/`Collection` сохраняется префикс направления.

`Редактор` выбирается только в Google Sheets. Новая строка получает значение `Редактор не выбран` и dropdown со значениями из `APPLICATION_EDITORS`.

### Миграция Старых Листов На Новый Порядок Колонок

Бот умеет читать старые листы без миграции. Если нужно физически переставить колонки в уже созданных одиночных листах, используйте отдельный CLI:

```bash
python -m app.sheet_schema_migration
```

По умолчанию команда работает в dry-run: она только показывает, какие секции старого формата найдены. Изменения в Google Sheets применяются только с явным флагом:

```bash
python -m app.sheet_schema_migration --execute
```

Точечный запуск для одного направления или листа:

```bash
python -m app.sheet_schema_migration --direction fl --sheet-name "29.06 (1)"
python -m app.sheet_schema_migration --spreadsheet-id "<spreadsheet_id>" --sheet-name "Срочные"
```

Скрипт мигрирует только предыдущую одиночную схему, где `Интент` был в `B`, `Статус` в `J`, `Редактор` в `K`. Новая схема, legacy/current технические схемы и массовые заявки не меняются. Миграция переносит `CellData`, поэтому сохраняет значения, rich text, форматирование и dropdown внутри переставляемых ячеек.

Перед `--execute` сделайте backup SQLite и желательно копию Google Sheet. Скрипт меняет внешние таблицы Google и не запускается автоматически вместе с ботом.

## Одиночная Заявка

Flow одиночной заявки:

1. Выбор направления.
2. Выбор типа ответа для `ФЛ`, `SME`, `АИ`.
3. Интент.
4. Закрепленный сценарист.
5. Кейс или сообщения клиента.
6. Суть изменений.
7. Исходный текст.
8. Признак срочности.
9. Финальная проверка.
10. Отправка.

GigaChat используется только для одиночных заявок. Он объединяет переданные поля в один текст и не проверяет заполненность направления, типа ответа, типа изменения или любого другого отдельного поля.

Проверка ищет прямые подтверждения трех критериев: содержание изменения, ситуацию применения и, только для изменения существующего ответа, причину изменения. Для нового ответа, акции, продукта, услуги, правила или инициативы причина не требуется: достаточно маркера новизны, конкретного содержания и ситуации применения.

Для существующего ответа действие может выражать добавление, удаление, замену или корректировку конкретного содержания. Перечисленные глаголы служат примерами: однозначные смысловые синонимы также принимаются. Текущей проблемой считается прямое описание ответа бота, наблюдаемая проблема клиента либо уже произошедшее изменение правил, условий, тарифов, ограничений или процесса.

Фразы вроде `новый ответ`, `поправить`, `по результатам анализа`, `задача от заказчика`, `для удобства` и ссылка без пояснения сами по себе ничего не подтверждают. Они не вызывают автоматический отказ, если конкретные сведения присутствуют в другом фрагменте заявки. GigaChat не составляет финальный текст и не придумывает отсутствующие сведения.

Если информации недостаточно, бот дает одну конкретную инструкцию по дополнению поля. Ответ сценариста добавляется ниже первоначальной сути изменений. После единственного уточнения сценарий продолжается; при сохраняющейся неоднозначности заявка получает статус `needs_attention`. Числовая `LLM оценка` больше не рассчитывается и остается пустой. Если GigaChat недоступен или ответ не удалось разобрать, заявка не блокируется: бот сохраняет пользовательский текст со статусом `error`.

Блокер содержит точную ссылку на невыполненное правило: `Критерий 1, правило 1.1`, `Критерий 1, правило 1.2`, `Критерий 2, правило 2.1` или `Критерий 3, правило 3.1`. Проверка останавливается на первом невыполненном правиле.

## Массовые Заявки

Массовый режим не использует xlsx-файл в боте. Бот создает место в Google Sheets, а пользователь заполняет строки сразу в таблице.

Flow массовой заявки:

1. Пользователь выбирает `Массовая заявка`.
2. Выбирает направление.
3. Выбирает место: `Срочные`, `Недельные` или `Интеграции`.
4. Выбирает тип изменения: `ADD`, `EDIT` или `CHIPS`.
5. Вводит количество строк, максимум `BULK_MAX_ROWS`.
6. Бот вставляет ровно это количество пустых строк в конец нужной рабочей секции и подсвечивает обязательные для заполнения колонки. `Закрепленный сценарист` выделяется нейтральным цветом, остальные обязательные поля — мягким желтым. Толстые границы ставятся только после успешной регистрации фактически заполненных строк.
7. Пользователь заполняет строки в обычных колонках выбранной схемы. Статус остается пустым до регистрации.
8. Пользователь нажимает `Заявка заполнена`, после чего бот регистрирует заполненные строки как обычные одиночные заявки, выдает `ID заявки`, ставит статус `Новая`, восстанавливает dropdown `Статус`/`Редактор` и оставляет `ID пачки` пустым.

GigaChat в массовом режиме не вызывается. Пустые строки внутри резерва игнорируются и остаются в таблице как ручной резерв; частично заполненная строка блокирует регистрацию до исправления.

Создание резерва защищено section-lock по конкретной секции листа и Google `developerMetadata`. Если metadata временно недоступна, бот не вставляет строки вслепую. Повторное подтверждение создания или регистрации не создает дубли; зависшую регистрацию можно повторить после `BULK_REGISTRATION_STALE_SECONDS` (`600` секунд по умолчанию).

В листах `Срочные` и `Интеграции` новые одиночные заявки и новые массовые резервы группируются по дневным блокам `ДД.ММ.ГГ`. ADD/EDIT и CHIPS используют отдельные блоки внутри своих секций. Старые строки не перестраиваются автоматически. Если nightly maintenance не сработал, первая заявка дня создаёт нужный блок сама.

## Дашборд

Дашборд является read-only представлением. Источник правды для статусов, комментариев и итоговых ответов - рабочие таблицы направлений.

В дашборде используется один лист `Заявки`: все зарегистрированные строки, включая строки из нового массового резерва, отображаются отдельными заявками. `ID пачки` заполняется только для legacy `bulk_batches`; новые `bulk_reservations` оставляют это поле пустым.

Схема листа `Заявки`:

1. `ID заявки`
2. `ID пачки`
3. `Дата заявки`
4. `Направление`
5. `Тип заявки`
6. `Тип ответа`
7. `Срочная`
8. `Автор заявки`
9. `Статус`
10. `Редактор`
11. `Итоговый ответ есть`
12. `Ссылка на рабочую строку`

Бот создает или обновляет строку дашборда по `ID заявки`. Для legacy `bulk_batches` поддержана старая проекция пачки, но новый массовый workflow создает только application-проекции по каждой зарегистрированной строке. Требуемая проекция сначала сохраняется в SQLite `dashboard_outbox`, поэтому недоступность Google Sheets не меняет успешный результат создания или регистрации заявки. Несколько изменений одной сущности объединяются в последнюю версию.

Один проход синхронизации читает лист `Заявки!A:L` один раз и применяет накопленные изменения одним `batchUpdate`. Дубли объединяются без потери даты, ссылки, статуса, редактора и признака итогового ответа, после чего лишние строки удаляются снизу вверх.

## Уведомления

Polling читает рабочие таблицы направлений каждые `STATUS_POLLING_INTERVAL_SECONDS` секунд. Обнаруженное событие и новое tracking-состояние атомарно записываются в SQLite `notification_outbox`, а требуемое состояние дашборда — в отдельный `dashboard_outbox`. Telegram-доставка и запись дашборда выполняются независимо, поэтому ошибка одного внешнего сервиса не откатывает уже сохраненное событие.

Outbox повторяет отправку с ограниченным backoff, восстанавливает зависшие записи `SENDING` и сохраняет порядок сообщений каждого пользователя. Длинные сообщения делятся на HTML-безопасные части до `NOTIFICATION_MESSAGE_MAX_CHARS`.

Бот хранит `message_id` текущего навигационного сообщения пользователя. При переходе к
новому шагу предыдущая inline-клавиатура отключается. Callback от старого сообщения не
передается в workflow и получает ответ о том, что кнопка устарела. Исключения:
`Заявка заполнена` для массовой пачки и `Главное меню` из фонового уведомления.

Для одиночных заявок автор получает уведомление при переходе в:

- `Итоговый ответ готов`
- `Принята`
- `Отклонена`
- `Отложена`

Для массовой заявки уведомление отправляется при переходе статуса всей пачки в `Готова`. Дополнительно бот присылает одно сгруппированное сообщение, если внутри пачки появились новые строки со статусом `Нужны пояснения`; в нем перечисляются заявки и комментарии редактора. Повторное уведомление по неизменившейся строке не отправляется. Переход в `В работе`, статус `Принято` и итоговые ответы строк уведомлений не создают.

Для одиночной заявки итоговый ответ отправляется только после перехода в статус `Итоговый ответ готов`. Комментарий редактора отправляется автору не по статусу, а после того как поле `Вопросы/комментарии редактора` остаётся одинаковым 3 polling-цикла подряд. Для срочных одиночных заявок ответ сценариста из поля `Ответ сценариста` отправляется в чат редакторов по той же стабилизации в 3 polling-цикла.

## Надежность И Резервные Копии

- Одиночная отправка идемпотентна по `application_id`: маршрут фиксируется до первой записи, а повтор сначала ищет существующую строку.
- Для временных ошибок Google API (`429`, `5xx`, timeout, broken pipe, reset соединения) используется ограниченный exponential backoff с jitter.
- SQLite работает с `WAL`, `synchronous=NORMAL`, `foreign_keys=ON` и `busy_timeout=10000`.
- Healthcheck проверяет свежесть heartbeat, целостность SQLite, обязательную конфигурацию,
  Telegram `getMe` и доступ service account к рабочим Google-таблицам. Внешний результат
  кэшируется на пять минут; после ранее успешной проверки один временный сбой допускается,
  второй подряд переводит контейнер в `unhealthy`.
- Docker-логи ограничены пятью файлами по 10 МБ.
- Завершенные массовые заявки не читаются в каждом частом polling-цикле.

Параметры внешней части healthcheck:

- `HEALTH_EXTERNAL_CHECK_INTERVAL_SECONDS=300` — интервал реальных запросов к Telegram и Google;
- `HEALTH_EXTERNAL_FAILURE_THRESHOLD=2` — число последовательных ошибок после первого успеха;
- `HEALTH_EXTERNAL_TIMEOUT_SECONDS=10` — timeout одного внешнего запроса;
- `HEALTH_EXTERNAL_CACHE_PATH=/data/external-health.json` — атомарный кэш результата.

Четыре рабочие таблицы направлений обязательны для состояния `healthy`. Дашборд проверяется
только при заполненном `GOOGLE_DASHBOARD_SPREADSHEET_ID`.

Локальный backup с проверкой `integrity_check`:

```bash
docker compose --profile maintenance run --rm backup
```

Проверка и восстановление в отдельный файл:

```bash
python -m app.maintenance verify backups/app-YYYYMMDD-HHMMSS.db
python -m app.maintenance restore backups/app-YYYYMMDD-HHMMSS.db restored.db
```

Примеры systemd unit для ежедневного запуска в 03:00 по Москве находятся в `ops/systemd`. Перед восстановлением production-базы контейнер должен быть остановлен; команда restore не должна указывать на активный `/data/app.db`.

## Ручная Проверка

1. Создайте Google-таблицы направлений и дашборда.
2. Дайте service account права редактора во всех таблицах.
3. Заполните `.env` новыми `GOOGLE_*_SPREADSHEET_ID`.
4. Запустите `docker compose up bot`.
5. Создайте одиночную заявку в Telegram и проверьте появление строки в недельной или интеграционной вкладке.
6. Измените статус или итоговый ответ в рабочей таблице и дождитесь уведомления в Telegram.
7. Создайте массовую заявку, вставьте строки в подготовленный блок, нажмите `Заявка заполнена` и проверьте регистрацию строк.

## Открытые Вопросы

- Срочные ADD/EDIT записываются в общую верхнюю таблицу листа `Срочные`, CHIPS — в отдельную нижнюю секцию.
- Для раскатки и каждой заполненной строки массовой заявки обязателен `Тип изменения`: `ADD`, `EDIT` или `CHIPS`.
- Новая массовая заявка создаёт резерв строк в выбранной рабочей секции; старый лист `Массовый ввод` остаётся только для legacy-сценариев.
- Автоматическая миграция старых Google Sheets `Высокий`, `Низкий`, `Массовые` в новую модель не выполняется.
- Ответ сценариста через Telegram пока не реализован; пользователь получает ссылку на рабочую строку.

## Одиночные заявки CHIPS

Для одиночной заявки типа `Раскатка` или `Срочные` с типом изменения `CHIPS` используется отдельный сценарий без GigaChat: `Закрепленный сценарист` → `Интент` → `Причина` → `Текст до чипса` → `Текст чипса` → `Текст после чипса` → проверка и отправка. Все шесть полей обязательны. Telegram-форматирование трёх текстовых фрагментов сохраняется отдельно.

Новая секция CHIPS в недельной вкладке содержит рабочие колонки `A:K`: `Закрепленный сценарист`, `Статус`, `Причина`, три текстовых фрагмента, `Комментарий качества`, `Вопросы/комментарии редактора`, `Ответ сценариста`, `Редактор`, `Интент`. Служебные поля находятся в `L:U`; удалять их нельзя. Dropdown статуса применяется к `B`, dropdown редактора - к `J`.

Если старая секция `CHIPS` пуста, бот заменяет только её заголовок новой схемой. Если в ней уже есть заявки, строки и заголовок сохраняются, а бот создаёт рядом секцию `CHIPS V2` и направляет новые заявки туда. Старые и новые секции продолжают участвовать в polling. Для CHIPS бот уведомляет об изменениях важных статусов и отправляет стабильный комментарий редактора из поля `Вопросы/комментарии редактора`, но не ожидает и не отправляет итоговый ответ редактора.

В листе `Срочные` используется смешанная структура: существующая общая таблица ADD/EDIT остаётся сверху, а маркер `CHIPS` и новая CHIPS-шапка находятся снизу. При первом запуске после обновления бот добавляет отсутствующую секцию в конец существующего листа без преобразования старых строк. Последующие ADD/EDIT вставляются перед маркером, поэтому не смешиваются с CHIPS.

Массовые заявки используют новую модель резерва строк в целевой секции. Для CHIPS применяется та же CHIPS-схема, что и для одиночных заявок; GigaChat в массовом режиме не вызывается.
