# Отчет по переносу Telegram-бота в eXpress

Дата подготовки: 27.05.2026

## 1. Executive summary

Текущий проект - Telegram-бот для сбора заявок на изменение сценариев и ответов чат-ботов. Он пошагово собирает данные от сценариста, проверяет поле "Суть изменений" через GigaChat, сохраняет черновики и служебные данные в SQLite, отправляет подтвержденные заявки в Google Sheets и уведомляет автора о важных изменениях статуса.

Аналогичный функционал в eXpress реализуем, но это не будет простой заменой `aiogram` на другой SDK. Основное архитектурное отличие: текущий Telegram-бот работает через polling и сам забирает события из Telegram, а eXpress-бот должен принимать входящие callback-запросы от CTS на доступный URL и отправлять ответы через BotX API.

Для внутреннего контура перенос выглядит технически реалистичным при условии, что bot-сервер имеет двустороннюю сетевую связность с CTS и разрешенный доступ к нужным корпоративным интеграциям. Для внешнего контура реализация также возможна, но требует отдельной проработки периметра: TLS, DMZ/reverse proxy, allowlist, секреты, журналирование, доступность Google Sheets и GigaChat из внешнего сегмента.

Ключевой вывод: бизнес-функционал можно сохранить почти полностью, но транспортный слой, идентификация пользователей, модель входящих событий, отправка файлов и безопасность контуров требуют отдельной реализации и тестирования на конкретной инсталляции eXpress.

## 2. Использованные источники eXpress

Документация, на которую опирается анализ:

- [Chatbots overview](https://docs.express.ms/chatbots/)
- [BotX Notifications API](https://docs.express.ms/chatbots/developer-guide/api/botx-api/notifications-api/)
- [Bot API command callback](https://docs.express.ms/chatbots/developer-guide/api/bot-api/command/)
- [Bots API token flow](https://docs.express.ms/chatbots/developer-guide/api/botx-api/bots-api/)
- [Chats API](https://docs.express.ms/chatbots/developer-guide/api/botx-api/chats-api/)
- [Users API](https://docs.express.ms/chatbots/developer-guide/api/botx-api/users-api/)
- [Files API](https://docs.express.ms/chatbots/developer-guide/api/botx-api/files-api/)
- [Deployment guide](https://docs.express.ms/chatbots/developer-guide/deployment-updating/deployment/)

Из документации eXpress важны следующие подтвержденные факты:

- BotX API содержит методы для ботов, уведомлений, событий, чатов, пользователей и файлов.
- Исходящие сообщения бота отправляются через direct notifications, поддерживают текст, metadata, keyboard и bubble-кнопки.
- Входящие пользовательские действия приходят на callback-метод бота как команды с `command.body`, `command.data`, `command.metadata`, `attachments` и блоком `from`.
- Пользователь в eXpress идентифицируется не Telegram ID, а `user_huid`, AD-логином, AD-доменом и другими корпоративными атрибутами.
- Для файлов есть отдельный Files API на скачивание и загрузку.
- Для развертывания чат-бота требуется отдельный сервер и сетевое взаимодействие между bot-сервером и CTS в обе стороны.

## 3. Текущий функционал Telegram-бота

### 3.1 Назначение

Бот автоматизирует сбор заявок на изменение сценариев и ответов чат-ботов. Основная ценность - превратить свободный текст сценариста в структурированную заявку, нормализовать описание через GigaChat и передать результат редакторам в Google Sheets.

### 3.2 Основные сценарии

| Сценарий | Что делает сейчас |
|---|---|
| Старт и меню | Команды `/start`, `/new`, кнопки выбора режима: одиночная заявка, массовая загрузка, дефолты. |
| Одиночная заявка | Пошаговый сбор 6 полей: интент, закрепленный сценарист, причина изменений, суть изменений, исходный текст, приоритет. |
| Черновик | Один активный черновик на пользователя хранится в SQLite; можно продолжить, начать заново, отменить, вернуться назад. |
| GigaChat | Проверяет "Суть изменений", возвращает нормализованное описание, оценку, проблемы и при необходимости один уточняющий вопрос. |
| Review | Перед отправкой показывает итоговую заявку, разрешает отправить или отредактировать любое поле. |
| Google Sheets | Записывает заявки в листы по приоритету: высокий и низкий. Создает листы, заголовки, dropdown статусов, цветовое оформление. |
| Статусы | Поддерживает статусы: новая, в работе, нужен ответ сценариста, ответ получен, принята, отклонена, отложена. |
| Уведомления | Фоновый polling Google Sheets отслеживает важные статусы и отправляет автору сообщение со ссылкой на строку. |
| Массовая загрузка | Генерирует xlsx-шаблон и создает область в листе "Массовые" для ручной вставки строк. |
| Дефолты | Пользователь может сохранить интент и сценариста по умолчанию. |
| Форматирование | Для поля "Исходный текст" сохраняет жирный и зачеркнутый текст из Telegram entities и переносит их в Google Sheets rich text. |

### 3.3 Техническая реализация

Текущий стек:

- Python 3.12.
- `aiogram 3` для Telegram polling, callback-кнопок и сообщений.
- SQLite через `aiosqlite` для черновиков, настроек пользователя, отправленных заявок и массовых пачек.
- Google Sheets API через service account.
- GigaChat SDK для LLM-проверки.
- Docker/Docker Compose для запуска.

Ключевые особенности текущей архитектуры:

- входящие события не требуют публичного endpoint, потому что Telegram polling инициируется самим ботом;
- состояние пользователя привязано к `telegram_user_id`;
- внешняя рабочая очередь редакторов фактически находится в Google Sheets;
- уведомления по статусам зависят от фонового чтения Google Sheets;
- секреты и параметры берутся из внешних конфигурационных файлов и не должны попадать в отчет или репозиторий.

## 4. Матрица для созвона

| Блок | Можно сделать в eXpress | Нельзя или не подтверждено | Риски | Что уточнить |
|---|---|---|---|---|
| Пошаговая заявка | Да, через входящие команды и исходящие BotX-сообщения с кнопками. | Нельзя оставить Telegram polling как есть. | Нужно переписать transport layer. | Какая версия CTS и BotX доступна в целевом контуре. |
| Кнопки | Да, Notifications API поддерживает keyboard и bubble-кнопки с `command`, `label`, `data`, `metadata`. | Поведение UI может отличаться от Telegram inline keyboard. | Нужно проверить вид кнопок на web, desktop, mobile. | Какие клиенты eXpress используют сотрудники. |
| Текстовые ответы | Да, callback команд содержит тело команды и данные пользователя. | Нужно проверить детали для обычного текстового ввода без кнопок в конкретной версии. | Разная модель команд может потребовать явных команд или silent-кнопок. | Как в компании принято запускать ботов: командами, личным чатом, SmartApp. |
| Файлы xlsx | Да, через Files API можно работать с файлами. | Нельзя считать, что Telegram `answer_document` переносится 1:1. | Нужно реализовать загрузку/скачивание через BotX Files API и проверить лимиты. | Максимальный размер файла, политики DLP/антивируса, разрешенные типы вложений. |
| GigaChat | Да, логика LLM независима от Telegram. | Может быть нельзя ходить во внешний GigaChat из внутреннего контура. | Сертификаты, прокси, timeout, персональные данные в промпте. | Какой endpoint GigaChat разрешен для каждого контура. |
| Google Sheets | Технически да, если сеть разрешает. | В защищенном контуре Google может быть запрещен. | Вынос данных во внешний SaaS, service account, аудит доступа. | Остается Google Sheets или нужен внутренний аналог. |
| SQLite | Да для MVP, лучше PostgreSQL для промышленного контура. | SQLite нежелателен при горизонтальном масштабировании. | Потеря состояния при ошибках volume, сложный HA. | Требования к отказоустойчивости и резервному копированию. |
| Уведомления по статусам | Да, бот может отправлять direct notifications пользователям. | Нужно сопоставить Telegram ID с eXpress `user_huid`. | Ошибки доставки, права бота в чатах, пустой список получателей. | Как хранить связь заявки с пользователем: HUID, AD login, email. |
| Внешние пользователи | Возможно, если политики eXpress и CTS разрешают. | Не подтверждено без доступа к настройкам конкретной инсталляции. | Ограничения федерации, гостевого доступа, чатов, файлов и ботов. | Нужны правила работы внешнего контура и внешних пользователей. |

## 5. Карта соответствия Telegram -> eXpress

| Текущий элемент Telegram | Аналог в eXpress | Оценка переноса | Комментарий |
|---|---|---|---|
| `aiogram` polling | HTTP callback endpoint бота | Требует переработки | eXpress будет вызывать URL bot-сервера, а не ждать polling. |
| `Message.text` | `command.body` во входящем callback | Реализуемо | Нужно нормализовать команды и свободный текст. |
| `CallbackQuery.data` | `command.data` и `metadata` | Реализуемо | Удобно переносить текущие callback constants в JSON data. |
| `InlineKeyboardMarkup` | `keyboard` или `bubble` в direct notification | Реализуемо | Нужно проверить UX и ширину кнопок в eXpress-клиентах. |
| `message.answer` | `POST /api/v4/botx/notifications/direct` | Реализуемо | Потребуется BotX token и `group_chat_id`. |
| `answer_document` | Files API upload + сообщение со вложением | Реализуемо после проверки | Нужна отдельная реализация загрузки файла и привязки к сообщению. |
| `message.entities` | eXpress `entities` | Частично реализуемо | Документация показывает entities, но нужно проверить поддержку bold/strikethrough для входящего текста. |
| `telegram_user_id` | `user_huid`, `ad_login`, `ad_domain`, email | Требует миграции модели данных | Основной ключ пользователя нужно заменить или расширить. |
| Личная переписка с ботом | Personal chat bot-user через Chats API | Реализуемо | Для proactive-уведомлений нужен `group_chat_id` личного чата или получатель HUID. |
| HTML parse mode Telegram | Форматирование eXpress-сообщений | Частично | Нужно проверить точные поддерживаемые варианты форматирования в клиентах. |
| Telegram proxy | Сетевой доступ bot-сервера к CTS | Требует новой схемы | Для eXpress важнее входящий HTTPS endpoint и двусторонний маршрут с CTS. |

## 6. Предлагаемая архитектура eXpress-версии

### 6.1 Компоненты

Минимальная архитектура:

- `express-bot-service` - новое Python-приложение или адаптер вокруг текущего `ApplicationFlow`.
- HTTP endpoint для входящих команд от eXpress Bot API.
- BotX API client для получения токена, отправки direct notifications, загрузки/скачивания файлов, работы с чатами и пользователями.
- Слой адаптации клавиатур: текущие `KeyboardKind` и callback data преобразуются в eXpress `keyboard`/`bubble`.
- Слой адаптации пользователя: eXpress `user_huid`/AD login/email вместо Telegram ID.
- Хранилище состояния: SQLite для MVP или PostgreSQL для промышленной версии.
- Интеграции: Google Sheets и GigaChat, либо их внутренние аналоги.

### 6.2 Поток одиночной заявки

1. Пользователь открывает личный чат с ботом или вызывает команду.
2. CTS отправляет callback на URL bot-сервера.
3. Bot-сервер проверяет authorization/signature по требованиям eXpress.
4. Команда преобразуется в внутреннее событие: пользователь, чат, текст, data, attachments.
5. Существующая логика `ApplicationFlow` выполняет переход состояния.
6. Ответ `BotResponse` преобразуется в direct notification с текстом, metadata и кнопками.
7. При отправке заявки сервис пишет строку в Google Sheets или внутреннее хранилище.
8. Фоновый процесс проверяет статусы и отправляет пользователю уведомления через BotX.

### 6.3 Что можно переиспользовать

Можно переиспользовать почти без изменения бизнес-логики:

- модель шагов заявки;
- проверку обязательных полей;
- LLM-клиент GigaChat и промпты;
- Google Sheets submission service;
- status polling Google Sheets;
- генерацию application ID и batch ID;
- шаблон массовой загрузки;
- структуру статусов;
- логику user defaults.

Потребуется заменить или адаптировать:

- `src/app/bot.py` как Telegram transport layer;
- `src/app/keyboards.py` как Telegram-specific keyboard builder;
- `TelegramNotifierProtocol` и типы `aiogram`;
- сохранение `telegram_user_id` в базе;
- обработку форматирования Telegram entities;
- отправку файлов.

## 7. Внутренний контур

### 7.1 Целевая схема

Для внутреннего контура рекомендуется размещать bot-сервер в корпоративной сети рядом с CTS или в сегменте, где разрешено двустороннее взаимодействие:

- CTS -> bot-сервер: входящие callback-команды.
- bot-сервер -> CTS/BotX: отправка сообщений, файлов, запросы к чатам и пользователям.
- bot-сервер -> хранилище заявок: Google Sheets или внутренний аналог.
- bot-сервер -> GigaChat: через разрешенный корпоративный маршрут, proxy или внутренний endpoint.
- bot-сервер -> БД: SQLite/PostgreSQL.

### 7.2 Преимущества

- Лучше соответствует корпоративной модели безопасности.
- Проще ограничить доступ к боту и данным только сотрудниками.
- Можно использовать AD login, AD domain, HUID и корпоративные справочники.
- Проще реализовать аудит, резервное копирование и сетевые allowlist.
- Можно заменить Google Sheets на внутреннюю таблицу, БД, Service Desk или корпоративный workflow.

### 7.3 Ограничения и риски

- Если Google Sheets запрещен из внутреннего контура, текущая модель обработки редакторами потребует замены.
- Если GigaChat доступен только через внешний endpoint, потребуется согласованный шлюз.
- Нужно проверить, разрешены ли BotX API и callbacks в нужном сегменте.
- Нужно решить, оставлять ли SQLite или переходить на PostgreSQL.
- Нужно проверить политику хранения персональных и рабочих данных в LLM-промптах.

### 7.4 Рекомендация

Внутренний контур считать основным вариантом для сотрудников компании. Для MVP можно сохранить текущие Google Sheets и GigaChat, если это разрешено ИБ. Для промышленного запуска лучше заранее заложить заменяемый интерфейс хранилища заявок, чтобы уйти от Google Sheets без переписывания bot-сценария.

## 8. Внешний контур

### 8.1 Целевая схема

Для внешнего контура bot-сервер должен иметь URL, доступный для CTS. Практический вариант:

- reverse proxy или API gateway в DMZ;
- TLS-сертификат, согласованный с требованиями eXpress и корпоративной ИБ;
- проксирование только нужных callback endpoints к bot-сервису;
- исходящий доступ bot-сервера к BotX API;
- отдельные секреты, токены и service accounts для внешнего контура;
- строгие firewall/allowlist правила.

### 8.2 Преимущества

- Можно обслуживать сценарии, где CTS или часть пользователей находятся вне внутреннего сегмента.
- Проще разделить внешнюю интеграцию и внутренние сервисы через gateway.
- Можно построить демо или пилот, не раскрывая весь внутренний контур.

### 8.3 Ограничения и риски

- Повышенные требования к TLS, hardening, WAF/API gateway и журналированию.
- Нужно минимизировать данные, проходящие через внешний сегмент.
- Google Sheets и GigaChat из внешнего контура могут быть запрещены или потребуют отдельного NAT/proxy.
- Нужно проверить, может ли внешний пользователь взаимодействовать с корпоративным ботом, получать файлы, нажимать кнопки и отправлять вложения.
- Нужно исключить ситуацию, когда внешний endpoint становится несанкционированным каналом доступа к внутренним заявкам.

### 8.4 Рекомендация

Внешний контур использовать только после утверждения сетевой схемы и модели данных. Для MVP внешнего контура лучше ограничить функционал: создание заявки, просмотр собственного статуса, получение уведомлений. Массовую загрузку, редакторские комментарии и прямые ссылки на таблицы стоит включать только после проверки политик доступа.

## 9. Что можно сделать почти полностью

1. Пошаговое создание одиночной заявки.
2. Продолжение, отмена и перезапуск черновика.
3. Кнопки меню, навигации, выбора приоритета и review.
4. Пользовательские дефолты по интенту и сценаристу.
5. Проверка "Сути изменений" через GigaChat.
6. Запись заявок в Google Sheets или аналогичное backend-хранилище.
7. Отслеживание статусов и уведомления автора.
8. Массовые пачки через подготовленную область в таблице.
9. Генерация xlsx-шаблона при подтвержденной поддержке Files API.
10. Логирование и диагностика базовых ошибок.

## 10. Что потребует переработки

| Область | Почему требуется переработка | Что сделать |
|---|---|---|
| Transport layer | Telegram polling отсутствует в eXpress-модели. | Реализовать HTTP callbacks и BotX client. |
| Пользовательский ID | В eXpress другой набор идентификаторов. | Перейти на `user_huid`, хранить AD login/domain/email при наличии. |
| Кнопки | Формат кнопок другой. | Сделать adapter `KeyboardKind -> eXpress keyboard/bubble`. |
| Файлы | Отправка и прием файлов идут через BotX Files API. | Реализовать upload/download и обработку attachments. |
| Форматирование | Telegram entities отличаются от eXpress entities. | Проверить поддержку нужных styles и сделать fallback на plain text. |
| Уведомления | Нужен `group_chat_id` или HUID получателя. | Хранить chat/user mapping после первого взаимодействия. |
| Безопасность | Появляется публичный или внутренний HTTP endpoint. | Проверять bearer/signature, TLS, allowlist, replay protection. |
| Массовая загрузка | Текущий UX завязан на скачивание шаблона и ручную вставку в Google Sheets. | Рассмотреть вариант SmartApp или прямой upload xlsx в бот. |

## 11. Что нельзя подтвердить без доступа к корпоративной инсталляции

- Доступность BotX API в конкретном внутреннем и внешнем контуре.
- Версия CTS и поддерживаемая версия Bot API/BotX API.
- Политики внешних пользователей: могут ли они писать боту, получать файлы, нажимать кнопки, открывать ссылки.
- Реальные сетевые маршруты между CTS, bot-сервером, Google Sheets, GigaChat и БД.
- Ограничения на типы файлов, размер вложений и антивирусную/DLP-проверку.
- Требования к TLS-сертификатам и BotX SSL-сертификату в инфраструктуре заказчика.
- Наличие административного доступа для регистрации бота в панели CTS.
- Политики хранения данных заявок и LLM-промптов.
- Допустимость Google Sheets как рабочего хранилища в каждом контуре.
- Нужен ли SmartApp вместо или вместе с чат-ботом для массовой загрузки и редакторского workflow.

## 12. Возможные проблемы

### 12.1 Сетевые проблемы

- Bot-сервер должен быть доступен для callback-запросов CTS.
- Bot-сервер должен сам ходить в BotX API.
- Для внешнего контура нужно исключить лишние входящие маршруты.
- Для внутреннего контура нужно заранее проверить доступ к Google и GigaChat.

### 12.2 Проблемы идентификации

Сейчас заявка связана с `telegram_user_id`. В eXpress нужно выбрать основной ключ:

- `user_huid` - предпочтительный технический идентификатор;
- `ad_login` + `ad_domain` - полезно для связи с AD;
- email - полезно для отчетности и поиска;
- `group_chat_id` - нужен для отправки сообщений в конкретный чат.

Рекомендуется хранить все доступные атрибуты, но первичным ключом пользователя в eXpress-версии сделать `user_huid`.

### 12.3 Проблемы Google Sheets

Google Sheets остается слабым местом для защищенного корпоративного контура:

- данные уходят во внешний сервис;
- доступ зависит от service account;
- редакторы меняют статусы вручную, что сложно валидировать;
- polling может пропустить временные ошибки без полноценной retry-очереди;
- прямые ссылки на строки могут быть недоступны части пользователей eXpress.

Рекомендуется обсудить, остается ли Google Sheets на MVP или сразу нужен внутренний аналог.

### 12.4 Проблемы LLM

GigaChat используется для нормализации описания изменений. Нужно определить:

- какие данные можно отправлять в LLM;
- нужен ли маскинг персональных данных;
- какой endpoint GigaChat разрешен;
- где хранить промпты;
- как логировать ошибки без утечки содержимого заявок.

### 12.5 Проблемы UX

eXpress-клиенты могут отличаться от Telegram:

- кнопки могут выглядеть иначе;
- silent-кнопки и bubble-кнопки нужно проверить на web, desktop, iOS, Android;
- длинные сообщения имеют лимит, в документации для direct notification указан лимит тела 4096 символов;
- форматирование исходного текста может быть ограничено;
- массовая загрузка через чат может быть менее удобной, чем через SmartApp.

## 13. Рекомендуемый MVP в eXpress

### 13.1 MVP-1: внутренний контур

В MVP-1 реализовать:

- регистрацию бота в CTS;
- HTTP callback endpoint;
- получение BotX token;
- отправку direct notifications;
- меню и одиночную заявку;
- SQLite или PostgreSQL для черновиков;
- GigaChat-проверку;
- запись в Google Sheets, если разрешено;
- уведомления по статусам;
- минимальную обработку файлов для xlsx-шаблона.

Не включать в первый MVP:

- полноценную роль редактора внутри eXpress;
- замену Google Sheets на внутренний workflow;
- SmartApp;
- сложную историю комментариев;
- поддержку внешних пользователей.

### 13.2 MVP-2: внешний контур

После MVP-1 отдельно реализовать внешний контур:

- reverse proxy/API gateway;
- отдельные секреты и конфиги;
- allowlist источников CTS;
- ограниченный набор команд;
- отдельное логирование и мониторинг;
- проверку доступа внешних пользователей;
- запрет или маскирование чувствительных данных.

## 15. Итоговая оценка

| Критерий | Оценка |
|---|---|
| Функциональная реализуемость | Высокая для внутреннего контура, средняя для внешнего до проверки политик. |
| Сложность переноса | Средняя: бизнес-логику можно переиспользовать, transport layer нужно переписать. |
| Основной технический риск | Сетевое взаимодействие CTS <-> bot-сервер и различия Bot API с Telegram polling. |
| Основной организационный риск | Доступы, политики контуров, разрешение Google Sheets/GigaChat. |
| Рекомендуемый первый шаг | Прототип eXpress transport layer: callback endpoint, token flow, отправка сообщения с кнопками, прием нажатия кнопки. |
| Рекомендуемый контур для пилота | Внутренний контур. |

Финальный вывод: перенос в eXpress целесообразен и технически возможен. Для сотрудников компании лучше начинать с внутреннего контура, сохранить текущую бизнес-логику и заменить только мессенджерный слой. Внешний контур стоит проектировать как отдельную безопасную публикацию сервиса через периметр с ограниченным набором функций и отдельным согласованием ИБ.
